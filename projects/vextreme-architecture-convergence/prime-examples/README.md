# Pink Onboarding — Prime Examples

[VXG RealForever]

## Purpose

Prime examples preserve **worked, source-grounded examples of judgment and handoff construction** that a
fresh worker can study after reading the canonical orientation source.

They are not another process owner.

~~~text
PRIME_EXAMPLE
!= CANONICAL_PROCESS
!= WORKSTATE
!= EFFECT_AUTHORITY
!= REQUIRED ANSWER SHAPE
~~~

A prime example is useful when it preserves enough externally useful structure that another fresh
instance can construct a comparable handoff/review/evaluation **without inheriting the predecessor's
private reasoning or conclusions**.

## Why this directory exists

The Pink work produced two different reusable pressures:

1. a fresh reviewer changed its review disposition only after its own recommendation was challenged for
   causal basis and inverse cost;
2. a fresh blind planner produced a strong public-workspace plan, but the trial was contaminated because
   the outer handoff accidentally exposed current VexWork `docs/foundation/INDEX.md`, which names the
   later `public/workspace.json` surface.

Both are worth preserving.

The first is a positive prime example of self-correcting judgment.

The second is a prime example of **evaluation construction and contamination detection**. It must not be
misrepresented as clean blind proof.

## Status vocabulary

~~~text
PRIME_EXAMPLE
  pressure-tested example whose claimed property was actually observed

PRIME_EXAMPLE_CANDIDATE
  useful worked example not yet proven across enough pressure

CONTAMINATED
  an evaluation result whose blindness / independence claim was invalidated

SUPERSEDED
  example retained for history but no longer recommended as current construction guidance
~~~

## How to use these examples

A fresh worker should:

~~~text
1. read current canonical orientation source;
2. read the current Pink project entry / checkpoint far enough to know why an example is relevant;
3. open the nearest prime example;
4. use PRIME-EXAMPLE-TEMPLATE.md to construct the new case;
5. fill source coordinates and visibility boundaries from the actual current work;
6. do not copy the prior example's conclusions into the new prompt;
7. perform a source-leak audit before sending a blind handoff;
8. after the result, record what actually generalized and what did not.
~~~

The examples show **construction relationships**, not answers.

## Promotion boundary

Do not promote this directory into a global VexWork foundation merely because the examples are useful.

Promotion requires materially different consumers showing that the same construction pattern recurs and
that project-local examples create avoidable reconstruction burden.

~~~text
ONE PROJECT'S PRIME EXAMPLES
!= GLOBAL TEMPLATE AUTHORITY

REPEATED INDEPENDENT PRESSURE
-> MAY EARN PROMOTION
~~~
