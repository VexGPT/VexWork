`[VXG RealForever]`

## Purpose

Give a fresh Vex/Devex instance one durable, dependency-ordered route from the current VexBoard/VexBusinessFactory architecture to one lived, teachable, replayable Vex Universe proof, while allowing any one instance to complete only the next grounded edge.

This is a continuity map, not a demand that one conversation complete the entire epic.

Permanent:

```text

PARTIAL_COMPLETION != FAILURE

PROCESS_MAP != EFFECT_AUTHORITY
```

# 3. First foundation horizon

The first meaningful foundation-complete state is not “all Vex Universe projects finished.”

It is:

1. a fresh instance can understand the Vex Universe ownership lattice;
2. VexBusinessFactory can describe one real/synthetic business end to end;
3. VexBoard can render and traverse that process;
4. meaningful human-visible steps can carry screenshot/evidence references;
5. one synthetic/test commerce path can be executed and replayed;
6. the successful path can be extracted as a reusable template;
7. another fresh instance can continue without reconstructing this chat.

The first lived business proof is **Antique Plate / PHYSICAL_ONE_OFF**.

# 5. Website / commerce learning ladder

For small-business onboarding, teach the smallest deployment level that matches the business need.

```text
LEVEL 0
source-only synthetic fixture

LEVEL 1
static public storefront
GitHub Pages / HTML / CSS / JS

LEVEL 2
hosted payment route
e.g. provider-hosted checkout/payment link

LEVEL 3
local backend learning adapter
Node or PHP
test secrets
test webhooks

LEVEL 4
hosted thin backend
secret storage
dynamic checkout
webhook handling
small order store

LEVEL 5
operating commerce service
inventory reservation
admin/auth
returns/refunds
shipping
tax/accounting handoff
monitoring/backups
```

GitHub Pages is static. A local PHP example is useful for learning, but it requires a different host/runtime when deployed.

Prefer the repository's existing Node/JavaScript stack for the reference dynamic implementation unless a PHP profile is intentionally being taught.

# 6. Provider onboarding must be a process map

Never reduce provider setup to:

```text
[ ] connect payment provider
```

Teach:

```text
why this provider is needed
who owns the account
test vs live mode
what public identifier/link is safe
what secrets must never enter public source/screenshots
what success looks like
how provider events are observed
what happens on failure/refund
who fulfills the real obligation
what independent verification activates live state
```

A payment-provider Journey can become:

```text
choose route meaning
-> establish/inspect account
-> create test product/price
-> create hosted/test route
-> add public-safe button
-> complete test checkout
-> observe provider event
-> form order/fulfillment attention
-> exercise refund/failure
-> verify public/mobile flow
-> independently verify live destination
-> activate route
```

# 9. Fresh-instance operating contract

A successor should:

1. read this map;
2. re-ground current VexWork/VexBoard/VexWorld PR heads;
3. determine the smallest unconsumed edge;
4. continue that edge rather than reopening the entire architecture;
5. preserve accepted effects;
6. add screenshots only after the evidence substrate exists;
7. write back material causal movement;
8. stop only at a real authority/human/effect boundary or completed bounded outcome.

Do not require one instance to complete the whole epic.

A good handoff is:

```text
what was owed
-> what was completed
-> what failed/changed
-> exact durable refs
-> current next edge
-> held effects
-> one resume coordinate
```
