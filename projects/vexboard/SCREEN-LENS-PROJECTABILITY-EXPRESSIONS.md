This source preserves the current intention and implementation reasoning for the next Living Screen Lens evolution without reopening the completed Screen Lens currentness/projection-truth work and without activating the parked Scenario Playground.

## Human intention

The next Screen Lens step is to make already-created VexLife-Android experience structure perceptible as a set of source-supported **screen expressions** rather than forcing a person to infer those expressions from Kotlin, Compose and runtime wiring.

The desired experience is one source-backed Screen viewed through the existing four Lens faces while one shared expression context changes:

~~~text
                         one source-backed Screen

expression context
  Source defaults
  Paired
  Songs populated
  Albums selected
  Player open
  Connection menu open
  source-authored preview
  accepted golden
        |
        +----------------+----------------+----------------+----------------+
        |                |                |                |
        v                v                v                v
     Surface          Structure        Behavior          Depth
~~~

The expression is a viewing coordinate over already-owned truth. It is not a fifth Lens face, a second runtime, or an automatic Scenario Playground state.

## Reconciliation corrections before implementation

### 1. Toolbar actions are an additive projection correction, not an unchanged baseline

Current Android AppScreenBlueprint.appRegistration() already registers toolbarActions as Screen-owned additionalPlacements.

The accepted Lens currently counts 228 Screen elements / 56 pathways. Claude's proposed projector counts 232 / 60 before and after its Android patch because it includes four already-registered toolbar actions.

Therefore the truthful candidate statement is:

~~~text
accepted projection
  228 Screen elements
  56 pathways

+ previously omitted already-registered Screen toolbar actions
  4 elements
  4 typed pathways

candidate enhanced projection
  232 Screen elements
  60 pathways
~~~

That may be a valid enhancement, but it must be reviewed as an explicit projection expansion rather than hidden behind before == after.

### 2. Expression context is not automatically Scenario state

Claude's proposed expression implementation imports Board simulation condition vocabulary and labels ordinary source-supported selection/presentation/population changes as SCENARIO truth.

That coupling is not accepted by this plan.

~~~text
source-supported possible expression
!= BoardScenario

selection
!= simulation by definition

open presentation
!= simulation by definition

population example
!= simulation by definition
~~~

The parked Scenario Playground may later **consume** the expression/projectability substrate. It does not own the current Screen Lens expression model.

### 3. Evidence identity should not be rewritten to make a join convenient

The Conversation screenshot golden currently has its own evidence/preview semantic root while the production Family Conversation Screen has its own Screen identity.

Changing a golden root to the production Screen ID merely so VexBoard can join them would risk replacing an existing evidence identity with a consumer-friendly identity.

Preferred direction:

~~~text
production Screen identity
+ evidence / golden identity
+ shared renderer / explicit source relationship
-> VexBoard projects the relationship

missing truthful relationship
-> HELD

not:
VexBoard wants a join
-> rewrite one producer's identity
~~~

The Conversation golden change is therefore held until the rightful relationship is proven.

### 4. Android alignment must improve Android on its own terms

An Android change is a strong candidate only when it makes an already-owned relationship more lawful/addressable without changing product meaning.

Examples with strong current support:

~~~text
raw custom collection card
-> existing VexComposeScope / VexColumn / VexText
-> same product meaning
-> inherited semantic identity becomes inspectable

dynamic repeated rows
-> existing VexStableLazyColumn
-> feature-owned stable itemRef
-> repeated-item mechanics remain with Android Elements
~~~

A change is weak when its main reason is "the VexBoard parser can understand this spelling."

### 5. The source reader is a bounded adapter, not a universal Kotlin interpreter

Claude's realization reader is useful evidence that a missing relation can be recovered from current source.

Its long-term ceiling is:

~~~text
bounded accepted Android patterns
-> read-only source relationship projection

NOT

arbitrary Kotlin
-> VexBoard invents semantic truth
~~~

The existing Screen Lens direction still points toward Android eventually exposing more of its own lawful projection from rightful runtime/source registries when repeated pressure earns that source contract.

### What differs materially

Direct VexFamily owns exact semantic admission at the semantic decision point:

~~~kotlin
override fun act(
    currentState: ThemeMode,
    control: Control,
): Act? =
    ...
        admit(
            control.mode.mode,
            begin = beginLatest(effect),
        )
~~~

So the accepted Act can answer:

~~~text
exact CURRENT State
+ exact Control
-> exact admitted State VALUE
+ Effect
+ execution Approach
~~~

The existing VexBehaviorBlueprint instead authors:

~~~kotlin
state<Current> {
    on(
        act = Act,
        effect = Effect,
    ).admit<NextState>()
}
~~~

and its relationship stores:

~~~text
from State KIND
Act
Effect
admitted State KIND
condition
~~~

The concrete Connection may then construct the actual admitted State value from runtime data and
checks that the value matches admittedStateKind.

That is a real ownership difference, not merely alternate Kotlin syntax.

### Screen Lens projection rule

Until consumer-driven convergence establishes otherwise, Screen Lens must **not collapse these two
grammars into one invented canonical Behavior schema**.

Instead, project what each rightful source actually proves.

For Direct VexFamily:

~~~text
Behavior
    Control + exact CURRENT State
    -> accepted Act
    -> exact admitted State value if authored
    -> Effect / Approach / RelationshipId where present
~~~

For existing SCAE / VexBehaviorBlueprint consumers:

~~~text
Behavior
    current State
    -> resolved Act
    -> Effect
    -> admitted State kind constraint

Depth / realization
    concrete Connection
    -> constructs the actual admitted State value
    -> realizes provider Effect
    -> reconciles provider observation
~~~

Permanent projection distinction:

~~~text
ADMITTED_STATE_VALUE
!=
ADMITTED_STATE_KIND

SEMANTIC_ADMISSION_OWNER
!=
CONNECTION_REALIZATION_OWNER

CURRENT_SOURCE_EXEMPLAR
!=
STABLE_BODY_MIGRATED_CONSUMER
~~~

If the source reader sees VexBehaviorBlueprint.admittedStateKind, it must not manufacture an
exact State value or imply that the stable Direct-Family ownership law is present there.

If a future Android migration moves VexStream/Maps onto Direct VexFamily, the adapter should
observe that source change naturally rather than carrying a permanent translation fiction.

## Shared projectability language

Before changing many components, implementation should stabilize the **questions** that both repositories need to answer.

Candidate relationship classes, not yet frozen wire schema:

~~~text
REGISTERED
  static semantic identity / placement exists

REALIZED_AS
  registered or runtime identity is realized by a concrete presentation structure

SELECTS
  a source-owned selection chooses one child/mode among lawful alternatives

PRESENTS
  a source-owned control/state makes transient presentation visible

POPULATES
  a runtime collection supplies repeated feature-owned items

CONDITIONED_BY
  source-owned provider/state truth changes presentation eligibility

EVIDENCED_BY
  a preview/golden/observed artifact demonstrates one expression
~~~

These describe relationships. They do not create new state owners.

## Expression context — candidate model

An Expression Context should be a **partial, source-supported assignment**, not a second full application state.

Candidate dimensions may include:

~~~text
selection
presentation
population
provider / connection condition
feature mode
evidence/reference variant
~~~

The exact dimensions should be earned by the patient zero rather than frozen as universal fields.

A useful mental model is:

~~~text
Screen
+ stable semantic identities
+ source realization relationships
+ bounded expression context
-> one resolved four-face Lens view
~~~

### Do not enumerate the Cartesian product

If a Screen has several selections, conditions, transient presentations and collections, blindly multiplying every possible value would create impossible states and combinatorial noise.

Instead derive a bounded representative set:

~~~text
1. source default
2. each source-declared axis changed independently where lawful
3. explicitly coupled states proven by source
4. source-authored preview/golden examples
5. accepted observed/lived evidence
6. later, explicitly proposed custom state only through the separately admitted Scenario/Design route
~~~

Source constraints reject impossible combinations.

A state should not exist in the expression rail merely because a combinatoric generator can form it.

## Repeated items, loops and the possible "vexItems" pressure

Do **not** create a new vexItems or custom loop ontology yet.

Current Android already owns an important reusable primitive:

~~~text
VexStableLazyColumn
  listRef
  feature-owned itemRef
  stable Compose key
  optional contentType
  visible-item projection
  emptyContent
  feature-owned itemContent
~~~

That is already a lawful answer to repeated runtime item identity.

For Screen Lens, the first question is whether this is enough to project:

~~~text
collection relationship
+ zero / one / many representative population
+ feature-owned runtime item refs
+ repeated row realization shape
~~~

without registering each runtime row as a fake static Screen element.

Permanent distinction:

~~~text
REPEATED_ITEMS != STATIC_SCREEN_REGISTRATION
LOOP_IN_BEHAVIOR_GRAPH != COLLECTION_RENDERING
PATHWAY_CYCLE != EXPRESSION_PERMUTATION
ITEM_COUNT != ITEM_IDENTITY
~~~

If VexStream plus a second materially different Android consumer demonstrate the same missing relationship, that pressure may earn a small portable relationship such as "repeated child / collection realization." The name and shape must be chosen from the repeated consumer need; it should not be invented now for naming symmetry.

## Planned implementation sequence

### Phase 0 — contract and invariant inventory

No product mutation.

- preserve accepted Screen Lens element/pathway identities and four-face semantics;
- classify each Claude handoff delta as **preserve**, **additive relationship**, **held**, or **reject/rework**;
- write the patient-zero expression questions before creating a generalized parser abstraction;
- explicitly separate Expression Context from Scenario state.

Exit condition: one source-grounded VexStream expression fixture can state what it needs from Android and VexBoard without changing either owner.

### Phase 1 — VexLife-Android projectability alignment

Use VexStream as the first real pressure source.

Candidate-first order:

1. custom VexStream collection/card presentation that can use existing Vex Compose identity inheritance;
2. Songs/Downloads repeated runtime rows through existing stable-list mechanics when those semantics are already feature-owned;
3. only the smallest shared list/container enhancement required by those real consumers;
4. preserve current runtime behavior, product wording, ordering, provider ownership and visual intent.

Do not perform broad raw-Compose migration merely because Screen Lens exists.

Do not change the Conversation golden identity in this phase unless the relationship is independently justified.

Exit condition: Android source has a consistent, Android-native way to expose the patient-zero relationships without VexBoard-specific annotations or duplicate state.

### Phase 2 — expression derivation and scalability

With the aligned Android patterns visible, study how expressions can be derived without redundant authored state.

Patient-zero expressions:

~~~text
Source defaults
-> Paired
-> Songs populated
-> Albums selected
-> Player active / docked
-> Full player open
-> Connection menu open
~~~

For each expression, prove:

~~~text
Surface    what becomes visible
Structure  what source/realization relationships participate
Behavior   what controls/conditions make it lawful
Depth      what runtime/provider/outside truth participates
~~~

Do not generate every permutation. Use source constraints and representative expressions.

Exit condition: the expression model can describe the VexStream sequence without Scenario ownership and without one-off per-expression parser rules.

### Phase 3 — VexBoard mapping language and components

Implement the smallest VexBoard-owned contract/components needed to render the same Expression Context across all four existing faces.

Recommended construction order:

~~~text
typed projectability/expression contract
-> source-backed fixture
-> expression resolver
-> four-face projection
-> expression rail / selection UI
~~~

The fixture lets the experience and contract prove themselves before the Kotlin source reader becomes the only producer.

Exit condition: a fixture and its resolved Screen Lens experience agree on identities and relationships.

### Phase 4 — Android source adapter / JSON projection

Only after the mapping language is coherent:

~~~text
accepted Android patterns
-> bounded adapter/source reader
-> derived projectability JSON
-> expression derivation
-> Screen Lens
~~~

The JSON is a projection/transport surface, not a new semantic owner.

The adapter must fail closed on unknown source shapes and preserve the accepted Lens baseline unless an additive change is explicitly named and reviewed.

Exit condition: adapter output matches the proven fixture contract and reproduces the patient-zero expressions from source.

### Phase 5 — round-trip proof and second consumer pressure

Prove:

~~~text
Android source
-> adapter projection
-> expression context
-> Surface / Structure / Behavior / Depth
-> expected screenshot/reference where available
-> lived/observed evidence
~~~

Then use one materially different consumer to pressure whether collection/condition/presentation relationships are genuinely reusable before extracting another shared abstraction.
