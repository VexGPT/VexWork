## Judgment before abstraction

Do **not** begin by inventing a universal composition framework.

The next shared contract must be earned by two concrete consumers that are structurally different.

### Consumer A — nested UI blueprint

Pressure a real screen/page composition such as:

```text
Screen
├─ header
├─ content
│  ├─ form
│  │  ├─ field
│  │  └─ submit button
│  └─ result / state region
└─ footer / navigation
```

The UI consumer should pressure:

```text
stable nested identity
semantic parent/child meaning
layout parent/child placement
structural order
resolved bounds
visual stacking
interaction identity
reusable component / template relationship
inspector reveal of nested refs
```

Start with the smallest layout-intent vocabulary that has real consumers:

```text
FREE
ROW
COLUMN
STACK
```

Do not prebuild GRID / FLEX / CONSTRAINT / platform-specific APIs until a real case earns them.

VexLife-Android Screen Blueprint / Elements / Vex Compose is useful realization pressure, but:

```text
VEXBOARD != COMPOSE
ANDROID_SYMBOL != PORTABLE_IDENTITY
TARGET_API_SYNTAX != BOARD_SEMANTICS
```

### Consumer B — reusable process blueprint

Pressure a process structure such as:

```text
Fulfillment
├─ Validate order
├─ PORTAL -> Payment
└─ PORTAL -> Delivery

Payment
├─ authorize
├─ decision
└─ outcome
```

The process consumer should pressure:

```text
stable process/module identity
explicit containment versus peer topology
PORTAL / detail-board descent
source/process refs
bounded neighborhood projection
where-used / backlink traversal
cross-board Journey continuity
reusable module identity without copied subgraphs
```

A process must not be forced to pretend it is a Screen merely to reuse layout machinery.

### Locality is part of correctness

A small edit should not randomly rearrange the understood board:

```text
small semantic / layout edit
-> preserve explicit anchors
-> inspect local occupancy
-> create room near affected region
-> move smallest necessary neighborhood
-> reroute affected connectors
-> preserve unrelated regions
```

### Connector routing is projection reasoning

Relationship direction remains semantic; visible route is projection.

Candidate routes should be ranked against current geometry using pressures such as:

```text
obstacle collision               forbidden / very high
node/container penetration       forbidden unless admitted
edge crossing                    high
label collision                  high
insufficient clearance           high
unrelated anchor movement        high
bend count                       moderate
route length                     moderate
preserve prior accepted route    preferred
lens reading direction           preferred when applicable
```

Do not freeze arbitrary numeric weights before proving cases earn them.
