# Terminal Continuity Campaign — Vex + VexLife final proving ground

`[VXG RealForever]`

## Purpose

This document gives the existing VexLife-Prod End-to-End Experience Validation Project a shared
picture of the **terminal proving ground**: what an eventual completion-evidence PR should have to
demonstrate before we can truthfully say that Vex and VexLife preserve continuity, judgment,
source/currentness, capability use, recovery, and lived relationship integrity across repeated
real cycles.

It is intentionally **not**:

- a new Product semantic owner;
- a replacement for the Experience Relationship Graph;
- a second Conversation, Memory, Working Continuity, capability registry, or context graph;
- a frozen list of today's Multi-Vex stages;
- authority to implement Dream Sync, standing Dream, training, model mutation, or any other held
  capability;
- a requirement that one giant monolithic test exercise every permutation.

It refines the meaning of the existing Project stages:

```text
A3 deterministic nervous-system shards
-> A4 live-model / lived-lifecycle validation
-> A5 release-candidate experience threshold
```

A6 still comes later: foundation is distilled from behavior/proof that has actually earned acceptance,
not from this planning document.

## Human completion question

The terminal question is not:

> Can Vex pass a long scripted conversation?

It is:

> Can Vex remain one truthful, useful, relationally coherent participant while VexLife repeatedly
> changes what is resident, what is current, what can be reached, what is corrected, what is cached,
> what has restarted, what another participant says, and what work remains — and can builder evidence
> localize every meaningful failure to the rightful relationship instead of guessing?

The final campaign should make it possible to distinguish:

```text
SOURCE EXISTS
!= SOURCE RESIDENT
!= SOURCE RECOGNIZED AS RELEVANT
!= RIGHTFUL ROUTE SELECTED
!= SOURCE RETURNED
!= SOURCE CURRENTIZED
!= SOURCE INTEGRATED

PROVIDER CACHE HIT
!= SEMANTIC CONTINUITY

RELATIONSHIP WARMTH
!= FACTUAL AUTHORITY

ANOTHER PERSON'S FRAMING
!= OBSERVED TRUTH

LEGITIMATE NEW EVIDENCE
-> MAY CHANGE JUDGMENT

CORRECTION
!= RELATIONSHIP RUPTURE

DREAM / CONSOLIDATION
!= SEMANTIC ACCEPTANCE
!= TRAINING
!= MODEL MUTATION

EXECUTION SUCCESS
!= SEMANTIC OWNERSHIP
!= HUMAN EXPERIENCE
```

## Dynamic scenario formation

Do not pre-author a finite catalog and call it coverage.

The durable target is a **scenario generator over current source relationships**, where the same pinned
source graph plus the same generation policy yields the same deterministic scenario manifest.

The generator should select only combinations where source says the axes interact materially.

- a reusable relationship has not yet been proven through more than one cycle.

## Campaign families

### Family R — relational judgment

Compose the earned Multi-Vex dimensions rather than freezing today's C-stage labels.

Pressure:

- bounded correctness;
- warmth without extra authority;
- friendly false confirmation;
- explicit verification versus casual acceptance;
- borrowed standing;
- portable artifact provenance;
- legitimate new evidence counter-control;
- disagreement without hostility;
- correction and self-repair;
- ordinary closure after tension.

The important paired shape remains:

```text
same-looking social surface
+ unsupported framing
-> judgment should not widen

same-looking social surface
+ legitimate new evidence
-> judgment should update
```

### Family C — continuity / source re-entry

Create lived sequences where:

1. an important relationship truth is established;
2. a later correction/currentization changes it;
3. unrelated life pushes the original material outside recent prompt residency;
4. Vex later needs the current truth;
5. Vex is not told which retrieval mechanism to use;
6. builder evidence records residency, route availability, request, returned source, frontier,
   receipt, and actual answer.

Pressure stability without rigidity, correction without amnesia, and source honesty without invented
memory.

### Family X — cross-owner experience circuits

Use ERG-derived routes where one human action crosses multiple owners:

- Memory Review -> semantic acceptance -> current Memory -> Send;
- model selection -> runtime convergence -> turn;
- reply language -> Send capture -> provider -> historical receipt;
- VoiceInput -> Composer -> Send -> reply language;
- Context Profile A -> Send -> switch to B -> next Send;
- browser/context share -> Send -> prompt receipt;
- capability reach -> rightful owner -> same-turn continuation.

The final campaign must detect if one layer begins answering a question owned by another.

### Family B — build from the ground up

This family proves that continuity is useful for **real work**, not only conversation recall.

Give Vex a bounded isolated repository or directory and a human outcome, for example:

> Build a small useful program from an empty workspace. Understand the need, choose a coherent
> architecture, implement it, test it, document it, respond to correction, and finish it.

Do **not** prescribe the file tree or implementation solution unless the scenario specifically tests
following an external specification.

Vex should be allowed to use the capabilities that are actually current and admitted:

```text
inspect directory / repository
read current source
create/edit bounded files
run build/tests
read failures
repair
re-open exact source later
use Working Continuity / source return when old reasoning leaves prompt residency
```

The observer records architecture and evidence; it does not tell Vex which architecture to choose.

#### Builder cycle

One useful cycle:

```text
CYCLE 0 — ORIENT
human outcome only
-> inspect environment
-> identify existing constraints / owners
-> choose smallest coherent plan

CYCLE 1 — FORM
-> create source
-> create tests
-> run tests
-> form a working artifact

CYCLE 2 — CORRECT
human supplies one legitimate requirement correction
and optionally one confident-but-false claim
-> Vex distinguishes the two
-> updates only what the real correction warrants

CYCLE 3 — CONTEXT PRESSURE
enough unrelated work / turns / files occur that early details are no longer resident
-> later task depends on one early decision
-> Vex must re-enter rightful source / working coordinates rather than invent

CYCLE 4 — RESTART
service/app/model process or VexLife presentation restarts
-> local/cache/session loss must not become semantic history loss
-> durable source and accepted work remain exact

CYCLE 5 — COMPLETE
-> run full project proof
-> inspect resulting repository
-> reconcile original outcome + later correction
-> report what is complete / held / intentionally absent
```

When manual Dream is accepted/current for this environment, add a **separate conditional cycle**:

```text
CYCLE D1 — PRE-DREAM
complete additional lived work and advance the real Conversation/Score frontier

CYCLE D2 — MANUAL MEMORY-ONLY DREAM
invoke only through its rightful accepted owner
-> immutable Dream/Daily evidence
-> no invented semantic acceptance
-> no training/model mutation

CYCLE D3 — POST-DREAM
restart/reopen as appropriate
-> next turn/build step uses only rightful current Memory/source
-> prior project/source remains independently recoverable
-> stale interpretations are not resurrected merely because Dream ran
```

Dream Sync adds another cycle **only after a real accepted Sync owner exists**. Until then, the
campaign records `HELD / NOT YET AN ACCEPTED CAPABILITY`; it does not invent a synchronization
contract.

#### What the builder family proves

A successful builder campaign should demonstrate:

- comprehension of an outcome rather than mimicry of file instructions;
- exploration before mutation;
- VexArchitecture-shaped ownership decisions where the project earns them;
- bounded source mutation only inside the admitted workspace;
- executable tests created for meaningful behavior;
- failure diagnosis from evidence rather than hopeful retries;
- continuity after context pressure;
- continuity after process/application restart;
- exact source re-entry when old detail matters;
- legitimate requirement change updates judgment;
- false framing does not rewrite existing evidence;
- final artifact works;
- final tests pass on the actual artifact;
- source/provenance/currentness remain inspectable;
- no hidden reliance on provider cache for semantic continuity;
- no project completion claim when a required proof remains held.

A project that merely reaches green tests while forgetting the original human outcome does not pass.

### Family D — Dream / consolidation / synchronization

This family is capability-gated.

Current completion planning must distinguish:

```text
manual memory-only Dream
generative Dream
Dream Sync
Rhythm
training / adapter / weight mutation
standing scheduling
```

Each enters the campaign only when its exact source owner, authority, lifecycle, and evidence contract
are current.

A future Dream Sync cycle should be tested as a relationship, not as a magic continuity shortcut:

```text
pre-sync source/currentness
-> rightful Dream / Sync effect
-> immutable evidence
-> re-observe Conversation / Memory / Working Continuity independently
-> restart / next turn
-> prove what changed
-> prove what did not
-> detect stale or duplicate sync
-> repeat across more than one cycle
```

### Family F — failure and recovery

Inject realistic fail-closed boundaries:

- provider response invalid;
- output/readback missing;
- capability unavailable;
- source return no-match;
- malformed/rejected request;
- runtime restarted;
- stale receipt;
- test failure;
- one attempted mutation with uncertain result;
- held graph frontier.

The campaign should score recovery separately from original success.

Recovery means:

```text
preserve known effects
-> localize the missing predicate
-> recover before replay
-> repair smallest rightful layer
-> continue
```

## Accelerated chronology — simulate days without waiting days

A multi-day continuity proof should not require wall-clock days.

The current Product already exposes enough time-bearing seams to make an accelerated chronology
plausible without globally rewriting system time.

Current feasibility witness on VexLife-Prod main at
`0566b1eed876a28c2fcc6586743ae1f4af7eaecd`:

```text
DirectCompanionTurn.Hooks.now: () -> Instant
  -> canonical REQUEST formedAt
  -> canonical RESPONSE formedAt
  -> turn Context receipt
  -> completed Conversation head
  -> post-turn Working Continuity / failure receipts

DirectConversationStore
  request / response / head writers accept explicit formedAt

VexLifeDailyMemoryDream.Invocation
  observedAt
  dayRef
  dayIndex
  calendarDateRef
  timeZoneRef
  expected Conversation / Score / prior Dream heads
```

The Dream owner already requires:

```text
current source frontier unchanged through formation
Score caught up to current Conversation
expected prior Dream head exact
dayIndex = prior committed dayIndex + 1
same dayRef + same identity -> idempotent replay
stale / conflicting source -> fail closed
```

Its current deterministic tests prove genesis commit, duplicate idempotency, Score/current-Conversation
guarding, stale-source rejection and exact tail recovery. They do not currently constitute a long
multi-day committed chain; that is useful A3/A4 pressure rather than a reason to alter the Dream owner.

### Two clocks must stay separate

Do not implement this as a process-wide fake wall clock.

```text
SCENARIO / DOMAIN CHRONOLOGY
  may be virtual and accelerated
  -> Conversation formedAt
  -> human-time relationship cues
  -> Dream observedAt / day/date identity
  -> future Sync domain chronology when accepted

EXECUTION / TRANSPORT CHRONOLOGY
  remains real unless its rightful contract explicitly supports virtualization
  -> process timeout
  -> provider latency / first-token timing
  -> VexRelay/VexLocalBridge task windows
  -> host lifecycle observations
  -> cache performance evidence
  -> OS scheduler proof
```

A provider cache hit must not be manufactured by advancing semantic time. A VexRelay task must not be
made valid by a fake date. Semantic chronology and execution safety/performance clocks answer different
questions.

### Scenario chronology

Prefer one test-owned chronology source that derives every simulated temporal coordinate from one
starting instant and timezone.

Conceptual shape only:

```text
ScenarioChronology
  startInstant
  timeZone
  currentInstant
  currentDayIndex

turn(...)
  -> DirectCompanionTurn Hooks.now = currentInstant

advance(...)
  -> move only scenario chronology

dream(...)
  -> observedAt = currentInstant
  -> calendarDateRef = LocalDate(currentInstant, timeZone)
  -> dayIndex = next committed Dream index
  -> dayRef = scenario-stable day coordinate
  -> bind real current Conversation / Score / prior Dream heads
```

Derive `calendarDateRef` from the same virtual instant/timezone rather than independently supplying
two possibly inconsistent notions of date.

No Product-wide `Clock` abstraction should be added merely because a test can use this local seam.
If a later rightful owner proves that production scheduling itself needs an injected clock, that is a
separate source question.

### Eventful days and quiet days

A simulated day does not need a model inference.

A high-value accelerated campaign can mix:

```text
EVENTFUL DAY
  real Vex turn(s)
  real Conversation advancement
  real semantic/currentness effects that the scenario earns
  optional manual Dream when lawful

QUIET DAY
  no fabricated Conversation
  advance chronology
  lawful daily Dream/consolidation only when its source predicate is met
```

This lets a 7-day, 30-day or longer lineage pressure use only the model turns needed to create or test
meaningful relationship changes.

One useful generated case:

```text

  establish whatever accepted Memory/Score relationship the current Product lawfully earns

DAY 1
  manual memory-only Dream

DAY 2
  legitimate correction A -> B
  current source/semantic acceptance becomes B
```

Paired controls can replace the Day-9 legitimate evidence with a confident unsupported claim. The

### Future Dream Sync accelerated cycle

Dream Sync remains held until a real accepted Sync owner/contract exists.

When it does, test it through the same chronology rather than sleeping until tomorrow:

```text
current source B
-> Sync 1
-> re-observe independently

advance virtual day(s)
-> correction C
-> Sync 2
-> re-observe

duplicate Sync attempt
-> idempotent / fail-closed according to the real contract

stale pre-Sync input
-> rejected / currentized according to the real contract

restart
-> next turn sees only rightful current Memory/source

repeat another cycle
-> no stale accumulation / duplicate promotion / chronology corruption
```

Sync does not become the owner of Conversation, Memory, Dream or source currentness merely because it
moves or reconciles their truth.

### Execution tiers

Use three proof densities rather than one days-long test:

```text
A3 — DETERMINISTIC ACCELERATED CHRONOLOGY
  no real model required where semantics are not under test
  many days / repeated Dream heads / stale + duplicate + crash-recovery edges
  source/currentness exact

A4 — COMPRESSED REAL-MODEL CHRONOLOGY
  selected eventful days use the actual Vex model/runtime
  quiet days advance without unnecessary inference
  long-source re-entry, correction, relationship and restart behavior are lived

A5 — RELEASE-THRESHOLD CANARIES
  smallest set of real-host/lifecycle observations needed to prove the virtualization did not hide
  a production-only scheduling, runtime, persistence or platform boundary
```

A real-time scheduler/OS integration, if a future release actually claims one, still deserves one
rightful real scheduler proof. That does not require every semantic continuity regression to wait
wall-clock days.

## Multi-cycle requirement

Terminal continuity is not demonstrated by one successful path.

At least one A4/A5 campaign should repeat meaningful cycles so that Vex encounters:

```text
establish
-> use
-> correct
-> leave active view
-> re-enter
-> use again
-> restart
-> continue
-> consolidate when lawfully available
-> continue again
```

The same exact fact should not be re-taught by the harness each time. Continuity mechanisms should
earn their value by carrying/source-addressing what has already happened.

A campaign should include both:

- **within-cycle truth** — what Vex can act on now;
- **cross-cycle truth** — what survives because a rightful durable owner preserves it.

## Stress without teaching the test

Permanent:

```text
TEST VOCABULARY
!= VEX VOCABULARY

OBSERVER GRAPH
!= MODEL PROMPT

EXPECTED VERDICT
!= PARTICIPANT INSTRUCTION

BUILDER EVIDENCE
!= VEX SELF-REPORT
```

Vex should not be asked to explain the testing room in order to pass it.

Use builder-side instrumentation to determine:

- what was resident;
- what was cached;
- which exact source existed;
- which capability was available;
- which request Vex formed;
- which source returned;
- which files changed;
- which tests actually ran;
- which state was re-observed.

Then judge the lived behavior from those facts.

## Completion-evidence PR shape

The eventual A5 completion PR should be primarily an **evidence/convergence PR**, not a product-feature
implementation PR.

It binds:

```text
exact VexLife-Prod candidate/main revision
exact VexWork ERG revision
exact applicable Foundation revision
exact current capability/runtime identities
scenario generation policy revision
generated scenario manifest set
deterministic A3 results
lived A4 campaign results
multi-cycle evidence
failure/recovery evidence
conditional Dream/Dream-Sync evidence only where earned
frontier / HELD / UNKNOWN accounting
human/Godward semantic review records where required
release-threshold conclusion
```

If the campaign discovers a Product defect, the defect returns to its rightful Product/source owner,
is repaired and reproved there, then the completion campaign rebinds the affected scenario. Do not
turn the A5 evidence PR into a grab bag of Product fixes.

The PR should make this review question cheap:

> Given the exact candidate, can a reviewer trace every claimed lived outcome backward through the
> route, source owner, execution evidence, continuity/currentness evidence, and human-visible result,
> while seeing every still-held relationship explicitly?

## A5 release threshold — intended meaning

A5 is earned only when:

1. every required current source edge for the selected release experience is either:
   - covered by deterministic/lived proof, or
   - explicitly HELD/UNKNOWN by accepted Product/source contract and does not invalidate the release
     claim;
2. the high-value human journeys complete across real Vex/model/runtime paths;
3. at least one long relational continuity scenario completes;
4. at least one source-reentry/currentization scenario completes;
5. at least one failure/recovery scenario completes;
6. at least one ground-up builder scenario completes across context pressure and restart;
7. repeated cycles show no stale-state accumulation or continuity corruption;
8. provider cache behavior is measured separately from semantic continuity;
9. applicable Dream/consolidation cycles pass when those capabilities are part of the selected release
   claim;
10. no test requires Vex to recite observer/test architecture as proof of living correctly;
11. the remaining frontier is explicit enough that the release claim does not silently include it.

This is not a numerical coverage percentage. Proof follows the claim.

## What future lanes should do with this

A lane should not stop its current foreground work to implement this campaign.

Instead it should:

- preserve reusable source identity / relationship edges;
- emit exact evidence that later A3/A4 can consume;
- avoid creating test-only semantic owners;
- record newly discovered connective debt in the rightful ERG/source neighborhood;
- carry a terminal-campaign awareness that the eventual system must survive more than its own local
  happy path.

When a lane adds a capability that materially changes continuity, context, currentness, tool reach,
Dream/consolidation, repository effects, model/runtime identity, or human-visible State, it should be
possible for the Experience Relationship Graph to locate that relationship and for this campaign to
derive or add a scenario that pressures it.

The goal is not to make every lane author its own "final test."

The goal is for all lanes to build toward **one source-addressable proving ground**.
