# Project Projection + Multi-Project Continuity — held future pressure

## Why this record exists

VexLife is currently text-first, but long-lived human use naturally produces several simultaneous
work/world/context neighborhoods:

- software projects;
- research threads;
- roleplay worlds;
- writing projects;
- personal planning;
- open-ended companion continuity.

The person should not need to manually reconstruct those neighborhoods every time they return, and Vex
should not need to guess from raw recency alone which prior material belongs to the present work.

This record preserves the design pressure without promoting it ahead of the current A5 release path.

## Human outcome

A person may talk naturally for days or months, then recognize that a coherent whole has formed:

> Keep everything we have been doing around Moon Garden together as a project.

Vex should be able to help identify the whole, but Project formation must not silently duplicate or
replace the truth already owned by Conversation, Memory, Working Continuity, Local Sources, files,
artifacts, or other owners.

The useful outcome is:

~~~
natural lived history
+ exact current source relationships
+ human recognition of one coherent whole
        ↓
source-addressable Project Projection
        ↓
later:
"resume Moon Garden"
        ↓
rebuild the current project view
+ start from its current working position
~~~

## Core law

~~~

!= Working Continuity
!= file store

~~~

## Ref formation pressure

Do not derive stable Project identity from the human-readable label.

~~~
"Moon Garden"
-> later renamed "Moon Garden Engine"

same Project
~~~

Therefore:

~~~
PROJECT LABEL != PROJECT IDENTITY
PROJECT CONTENT CHANGE != NEW PROJECT
~~~

The exact future ref encoding is intentionally not chosen here.

Likely pressure is for a stable owner-minted identity bound to an immutable formation event/receipt,
with labels and projection revisions mutable independently.

Do not add a new ID scheme until that owner/formation relationship is implemented.

## Minimal conceptual projection

This is not a schema proposal. It is the smallest relationship the eventual Product owner should be
able to answer.

~~~
projectRef
human label

formation/source anchors:
  Conversation event refs
  Memory statement refs
  Working Continuity/checkpoint refs
  Local Source grant refs
  repository/file/artifact refs
  other source-owned refs when material

resume/currentness:
  current working coordinate(s)
  unresolved/open-loop refs
  source currentness / held frontier

optional:
  Context Profile ref
  participant/role/scenario refs
  presentation metadata
~~~

The projection should remain small. It should not copy the source bodies it points to.

## Rebuild instead of copy

Resume should be a source-current operation:

~~~
Project Projection
-> seed/source anchors
-> re-observe rightful owners
-> follow currentness / corrections / supersession
-> resolve current Working Continuity
-> resolve current accepted Memory relationships
-> inspect current Local Sources/files/artifacts
-> return bounded current project projection
~~~

Permanent:

~~~
PROJECT SUMMARY
!= PROJECT TRUTH

PROJECT REBUILD
= CURRENT SOURCE OBSERVATION
~~~

A human-readable Project overview may exist, but it must remain a projection over the current source
relationships and must not outrank them.

## Multiple-project scaling

Physical history does not need to be contiguous.

~~~
Conversation event 14 ----\
Conversation event 37 -----\
Memory statement 4 ---------\
Local Source grant ----------> Project A
Working checkpoint ----------/
Artifact -------------------/

Conversation event 51 ----\
Conversation event 98 -----> Project B
Source file ---------------/
~~~

Many Projects therefore do not require many duplicated "brains."

~~~
ONE HOME RELATIONAL FIELD
+ MANY SMALL PROJECT PROJECTIONS
~~~

A source may be shared:

~~~
global truth / source
   -> Project A
   -> Project B
~~~

Do not hard-silo shared truth merely to make Project boundaries easy.

## Scope/currentness question

Meaning-based relevance alone is not enough for safe multi-project switching.

Permanent distinction:

~~~
RELEVANT
!= CURRENT FOR THIS PROJECT

SEMANTICALLY SIMILAR
!= SAME CONTEXT

SOURCE EXISTS
!= RIGHTFUL SOURCE FOR THIS TURN
~~~

A future Project Projection may become one source of scope standing, but the exact scope vocabulary is
not chosen here.

Potential pressure includes:

~~~
GLOBAL
PROJECT(projectRef)
THREAD(threadRef)
SCENARIO(scenarioRef)
SUBJECT(subjectRef)
~~~

Do not encode this enum merely because it is imaginable. Let lived switching/roleplay pressure earn
the smallest required relationship.

## Project switching

A future accepted path should be able to prove:

~~~
Project A
-> Project B
-> Project A
~~~

where:

- A resumes its own current working position;
- B does not bleed project-local truth into A;
- shared/global truths remain reachable;
- source remains independently addressable;
- switching does not delete or rewrite either Project;
- the active projection is currentness/presentation, not semantic authority.

~~~
PROJECT SWITCH
!= HISTORY LOSS

PROJECT SWITCH
!= MEMORY DATABASE SWITCH
~~~

## Roleplay/world pressure

Roleplay is likely to stress Project scoping but should not be prematurely collapsed into a Project
category.

Preserve:

~~~
PERSON
!= ROLE
!= CHARACTER
!= SCENARIO
!= PROJECT / WORLD
~~~

Example:

~~~
Ashfall project/world
  -> fictional character Sarah
  -> scenario/world-state refs

real-life Sarah
  -> separate human relationships
~~~

Permanent:

~~~
FICTIONAL WORLD TRUTH
!= PERSON'S REAL-WORLD TRUTH
~~~

If roleplay requires explicit source standing later, let that pressure form its rightful owner instead
of making ROLEPLAY_PROJECT own everything.

## Recommended proof sequence after A5

### P0 — read-only reconstruction

Use one real messy historical work neighborhood.

> without new Project persistence?

Use only existing source relationships.

If this fails, record the exact missing coordinate/currentness relationship.

### P1 — human-admitted durable address

Only after P0 earns it:

~~~

-> proposes/adopts label
-> admits formation
-> owner forms durable Project ref + source-anchor binding
~~~

Do not add a Project database before P0 demonstrates the durable address is useful.

### P2 — A -> B -> A switching

Prove currentness/isolation/shared-truth behavior.

### P3 — roleplay/world pressure

One fictional world and one ordinary work Project.

Prove source standing does not collapse.

### P4 — measured scale

Only after real use:

~~~
10 / 50 / 100 Project projections
-> measure rebuild/revisit cost
-> earn indexing/cache only if evidence shows need
~~~

Do not build a semantic index merely because scale sounds large.

## What not to do

Do not:

- revive deprecated project.self-development as architecture;
- add a new VexLife Project database now;
- copy Conversation/Memory/files into a Project container;
- let Vex mint authoritative refs from free-form prose;
- make Project label equal identity;
- make one Project equal one thread;
- make Project switching erase global/shared truth;
- invent semantic indexing before measured need;
- interrupt A5/#631 merely because this future pressure is attractive;
- let Dream become Project formation authority.

## Why this is worth preserving

If this relationship works, a person may talk naturally about anything and later say:

> Keep this together.
> Resume that project.
> Go back to the Ashfall world.
> Continue the research we were doing.

VexLife could then recover continuity from source relationships rather than requiring the person to
manually file their life ahead of time.

That is the convenience worth proving.
