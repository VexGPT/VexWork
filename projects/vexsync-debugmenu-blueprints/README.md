**Status:** VexBoard PR #155 remains a `CURRENT_SIBLING_CANDIDATE_REFERENCE`, still unmerged. Its earlier

~~~text

desktop.vexlife.vexstream.ConnectionStatus
web.vexlife.vexstream.ConnectionStatus
~~~

If the scope is reliably preserved, removing the `Origin` postfix loses no canonicality, identity,

~~~text

-> SAME SEMANTIC NOUN

CANONICAL VS REALIZATION ROLE
-> DIFFERENT SCOPE

SCOPE DIFFERENCE
!= PERMISSION TO MUTATE THE SEMANTIC NOUN

ORIGIN SCOPE
!= ORIGIN POSTFIX
~~~

collision does not justify permanently changing the canonical noun.

**Reopen condition:** a required representation genuinely loses scope/qualification and cannot preserve
canonical-vs-realization ownership through an explicit coordinate or metadata. That would pressure the
representation first, not automatically restore a noun postfix.

## Why Debug Menu is the first specimen

The current request is intentionally ordinary:

> As a user I want to be able to switch between dark and light mode in the Debug Menu.

It is useful because the human result is easy to understand while the implementation path exposes several
real architectural questions:

- how the user reaches Debug Menu;
- which existing semantic coordinates already represent that terrain;
- which identity belongs to the theme control;
- who owns current theme truth;
- whether the semantic relationship needs SCAE depth or a simpler typed relationship;
- how current Android realizes the meaning;
- which parts of that realization are reusable versus target-local.

The goal is not to pre-design the rest of Debug Menu.

## From-zero Origin construction — design first, targets later

The current Android specimen is useful evidence, but a new feature does **not** require an existing target
implementation before reusable meaning can be authored.

For a first-time feature request, the intended direction is:

~~~text
human request
-> preserve the intended lived result
-> discover the smallest reusable semantic nouns / values
-> form the canonical Origin design
-> compose Screens / Controls / content
-> express each edge with the smallest truthful typed relationship
-> add Behavior / Act / Effect only when the semantic problem earns them
-> accept the Origin design
-> map the accepted meaning into each target
-> scaffold target-native realization from the already-settled semantic categories
-> prove the lived result
-> reverse-map evidence back to the same Origin meaning
~~~

The Origin therefore does not describe Android code that already exists. It is the construction-grade
semantic design from which Android, Desktop, Web or another target can be formed.

### Canonical scope versus target realization scope

When a reusable semantic object needs a distinct canonical definition, canonicality is expressed by its
**Origin scope**, not by mutating its semantic noun.

~~~text
canonical reusable coordinate
  origin.<semantic-scope>.<SemanticNoun>

target realization coordinate
  <target>.<semantic-scope>.<SemanticNoun>

semantic identity
  stable semantic ID / relationship coordinate where independently required
~~~

Example:

~~~text
origin.<semantic-scope>.DebugMenuScreen
  screenId = screen.debug-menu

android.<semantic-scope>.DebugMenuScreen
desktop.<semantic-scope>.DebugMenuScreen
web.<semantic-scope>.DebugMenuScreen
  realize the same DebugMenuScreen meaning
~~~

Likewise, when ThemeMode earns independent canonical ownership:

~~~text
origin.<semantic-scope>.ThemeMode

android.<semantic-scope>.ThemeMode
desktop.<semantic-scope>.ThemeMode
web.<semantic-scope>.ThemeMode
~~~

The reusable noun remains exactly `ThemeMode`. `origin` identifies the canonical-definition role;
`android` / `desktop` / `web` identify realization roles.

~~~text
CANONICALITY
  = coordinate / scope responsibility

CANONICALITY
  != semantic noun suffix
~~~

This does not require every semantic child to receive an independent Origin-scope coordinate. Independent
canonical ownership is still earned through the Origin Eligibility / Exclusion test below.

### Typed relationship before Act identity

The authoring decision begins with the truthful meaning of the edge:

~~~text
destination relationship
  -> NavigateTo(ScreenId)

presentation relationship
  -> Open / Close / Dismiss

choice / value relationship
  -> Select / Set / Clear

state-dependent or independently meaningful behavior
  -> Behavior
  -> optional Act
  -> optional Effect
~~~

`NavigateTo` is an operation/relationship, not an identity.

~~~text
ControlId
  identifies the initiating Control

ScreenId
  identifies the destination Screen

NavigateTo(ScreenId)
  states the reusable intention
~~~

Do not manufacture an `ActId` merely because a Control was activated.

An Act becomes useful when the action itself is independently meaningful: for example it may be reused by
multiple Controls, invoked without a visual Control, admitted or denied by policy, selected differently
under State, observed/proved independently, referenced by another semantic object, or mapped to different
target mechanics while preserving one semantic action.

The Play/Pause exemplar demonstrates that threshold:

~~~text
State = Paused
+ Control = PlayPause
-> Act = Play

State = Playing
+ same Control
-> Act = Pause
~~~

By contrast:

~~~text
Control
-> NavigateTo(screen.debug-menu)
~~~

already contains the truthful navigation meaning and does not currently earn another Act identity.

## VexSync Origin Walk — incremental semantic construction

The current name for this step-by-step VexSync construction discipline is **Origin Walk**.

~~~text
one grounded question
-> one earned distinction
-> preserve why / pressure / provenance
-> expose the next unresolved question
-> continue
~~~

A fresh conversation does not restart the Walk. It resumes from the current **Walk Frontier** after
consuming the established relevant Origin Steps and examples.

Current process vocabulary:

~~~text
Origin Walk
  the whole incremental semantic-construction process

Origin Step
  one distinction that has earned a stable place in the current model

Walk Pressure
  the human need, observed problem, counterexample or relationship that forces the next question

Walk Frontier
  the exact unresolved semantic question where construction should continue

Origin Reground
  return to the earliest affected Origin Step when new evidence challenges an assumption,
  preserving upstream truth and reopening only dependent descendants

Origin Roundtrip
  Origin meaning -> target realization -> lived evidence -> reconstruction of the same meaning
~~~

### "Smallest" means minimum complete, not shortest

Earlier source used words such as `smallest` and `minimal`. The current project rule sharpens that language:

~~~text
SMALLEST / MINIMAL
  = MINIMUM COMPLETE

MINIMUM COMPLETE
  = nothing unnecessary
  + nothing materially necessary missing

MINIMUM COMPLETE
  != shortest sentence
  != fewest fields
  != compressed summary that loses the problems, reasons, invariants or provenance
     that make the next decision correct
~~~

The removal test is:

> Can this component be removed without losing correctness, human intention, a required case, rightful
> ownership, provenance, scalability, recoverability, or an important reason the design exists?

If yes, remove it. If no, it is part of the minimum-complete meaning or solution even when that requires
multiple explicit components.

### Conclusion and summary — compression must preserve justification

The Origin Walk does not use `conclusion` to mean "skip to the end" or "the final sentence."

A **Conclusion** is:

> a minimum-complete, simplified justification of what the evidence supports.

It therefore requires a visible support relationship:

~~~text
EVIDENCE
  grounded observations / source / proof

REASONING
  why those observations support or fail to support a claim

CONCLUSION
  the justified claim compressed enough to reuse
  without severing the material reasons that make it trustworthy
~~~

A statement with no supporting evidence is not promoted to a conclusion merely because it sounds final.

~~~text
UNSUPPORTED STATEMENT
  may be:
    question
    hypothesis
    proposal
    assumption
    working model
    assertion

UNSUPPORTED STATEMENT
!= CONCLUSION
~~~

A useful conclusion should preserve the causal path by which the conclusion became justified.

The current working flow is:

~~~text
CIRCUMSTANCE
  the grounded scenario / condition / evidence that existed

CONSEQUENCE / PRESSURE
  what became unideal, ambiguous, costly, unsafe, duplicated, fragmented or otherwise problematic
  and why that consequence matters

RESPONSE / CANDIDATE SOLUTION
  what change, mechanism or design was introduced to address that pressure

RESOLUTION EVIDENCE
  what the response actually addressed
  which original problems/cases were resolved
  which invariants were preserved
  what evidence shows the improvement rather than merely asserting it

CONCLUSION
  the minimum-complete justified claim that follows from the circumstance,
  pressure, response and resolution evidence
~~~

This ordering matters. A proposed response is not promoted to a successful solution merely because it was
implemented. The resolution evidence must show what pressure it actually addressed.

Optional guards may follow when they materially protect the conclusion:

~~~text
BOUNDARY
  what the conclusion does not claim / where its scope stops

REOPEN CONDITION
  what materially different evidence or pressure would require the conclusion to be reconsidered
~~~

Boundary and reopen condition are not substitutes for the causal justification. They protect scope and
currentness after the conclusion has already been earned.

The conclusion does not need to restate every raw artifact. It does need to preserve the summarized
causal justification and evidence coordinates required to understand why the conclusion currently survives.

A **Summary** has a different job:

> compress a larger body for orientation without erasing the causal/evidence route required to recover
> its meaning.

~~~text
SUMMARY
  may compress detail
  may group established conclusions
  may point to causal examples / evidence

SUMMARY
  must preserve material distinctions
  must not promote unsupported claims
  must not make omitted reasoning unrecoverable

SUMMARY
!= substitute truth owner
SUMMARY
!= "only read this and ignore why"
~~~

A good current-entry summary lets a fresh Builder orient quickly, then descend into the exact evidence /
causal episode when the next decision depends on it.

~~~text
ORIENTATION COMPRESSION
+ RECOVERABLE JUSTIFICATION
= useful summary

COMPRESSION
- WHY
- EVIDENCE
- REOPEN CONDITIONS
= reasoning loss
~~~

This distinction is why `CURRENT-EXAMPLES.md` exists beside the canonical README: the README can remain
the current entry while the companion preserves the evidence-backed causal evolution that a compact
orientation cannot safely carry in full.

### Problem and solution consideration

A **Problem** is currently treated as an observed or required mismatch between current reality and an
intended outcome/invariant whose consequences materially affect an admitted concern.

~~~text
Problem
  current truth
  + intended truth
  + material mismatch
  + consequences
  + materially distinct cases
~~~

Do not automatically split every case into another managed Work/owner. Several cases may be facets of one
structural problem until evidence shows independent ownership is required.

A solution can then be considered at increasing depth:

~~~text
PATCHED
  immediate symptom removed

RESOLVED
  admitted problem/cases satisfied

SYSTEMICALLY RESOLVED
  recurring underlying cause addressed

CONVERGED
  several related pressures resolved through one reusable architecture
  with less duplicated state / interpretation / responsibility

REFINED
  later pressure improves scale, clarity or simplicity
  without losing previously earned truth
~~~

Current convergence principle:

~~~text
prefer the architecture that resolves the largest coherent set of admitted pressures
with the fewest independent managed truths

while preserving every distinction that still has a rightful separate owner
~~~

"Manage less" does not mean collapse owners. One traversable causal path may still cross several rightful
owners.

### Reusable Solution Consideration Grammar

The problem/solution reasoning is intended to be reusable across future specimens, but it is not a flat
checklist that must be mechanically exhausted every time.

~~~text
question
-> grounded answer
-> answer exposes a new pressure
-> select the next relevant question family
-> continue
~~~

The stable question families currently include:

~~~text
PROBLEM FIT
  What problem is actually being solved?
  What is current truth?
  What is intended truth?
  What mismatch matters?
  What consequences and materially distinct cases make it a real problem?

SYMPTOM / CAUSE
  Is this the problem or only a visible symptom?
  Would removing the symptom leave the underlying mismatch intact?
  Could the apparent fix make the structural problem worse?

COMPLETENESS
  Which admitted cases does the solution satisfy?
  Which cases remain intentionally outside?
  What materially necessary reason would be lost by simplifying further?

RELATIONAL
  Who connects to this?
  What does it depend on?
  Who depends on it?
  What relationships appear, disappear or change because it exists?

COUNTERFACTUAL
  What happens if it is absent, collapsed, bypassed, duplicated or substituted?

CONVERGENCE
  Which duplicated truths, interpretations, responsibilities, synchronization points or recovery paths
  disappear?
  What new managed truth does the solution itself introduce?

OWNERSHIP
  Who owns each truth before and after the solution?
  Does the solution coordinate rightful owners or absorb their responsibilities?

STANDARDIZATION
  What happens if this becomes the normal way everyone solves this class of problem?
  Does every additional consumer make ownership/debugging easier or harder?

DIAGNOSTIC LEGIBILITY
  Can a failure be traced from observed result back through executor, target realization, semantic mapping,
  Origin relationship/state and originating human cause?

SCALE
  With 2 / 20 / 2,000 consumers, children, targets or transitions, what multiplies?

EVOLUTION
  When one child, target or requirement changes, what else must change?

RECOVERY
  After partial failure or restart, what truth can be recovered without replaying accidental caller history?

PROVENANCE
  Can a fresh Builder still explain why this architecture exists and which pressures made the choice win?
~~~

A reusable question is not automatically a required schema field. The questions protect reasoning quality;
durable fields are earned only when later consumers need the answer as source.

### Symptom removal is not automatically problem resolution

A brute-force/local fix can be valid, but its success level must remain explicit.

~~~text
symptom disappears
!= root mismatch resolved

one instance works
!= recurring cause removed

systemic
!= automatically converged

converged
!= final / immune to later refinement
~~~

The Walk should allow progression such as:

~~~text
brute-force fix
-> local structural fix
-> systemic fix
-> converged architecture
-> later pressure-tested refinement
~~~

The purpose is not to reject a bounded fix when it is the right current action. It is to avoid mistaking
"works here" for "this is the reusable architecture."

### Convergence is not centralization

A convergence mechanism is valuable when it reduces duplicated management while keeping rightful owners
legible.

~~~text
CONVERGENCE
  fewer duplicated truths / interpretations / recovery paths
  + one traversable causal path
  + rightful owners remain distinct

CENTRALIZATION
  one coordinator absorbs state / policy / effects / mapping / recovery
  that still belong to separate owners
~~~

Useful management-burden questions include:

~~~text
How many independent truths must stay current?
How many owners must coordinate?
How many relationship paths must stay synchronized?
How many recovery paths exist?
How many interpretations of the same human meaning can drift?
What new state does the convergence mechanism itself introduce?
~~~

One path does not require one owner.

### Minimum-complete meaning

When an Origin object or architectural boundary earns durable meaning, consider at least:

~~~text
WHAT
  what semantic thing is this?

WHY
  why does it need to exist?

PRESSURES RESOLVED
  which admitted problems/cases justify this boundary?

INVARIANTS
  what must remain true if children or target realization change?

RELATIONAL ROLE
  who/what does it connect to, depend on, feed, coordinate with or deliberately not own?

ABSENCE
  what becomes impossible, duplicated, fragmented, ownerless or incorrectly coupled without it?

BOUNDARY
  what truth belongs here and what truth remains elsewhere?
~~~

These are **reasoning questions**, not mandatory schema fields. A field is introduced only if a consumer
needs the answer as durable independently addressable source.

### Relational and counterfactual question grammar

A node cannot be validated only from its internals. The Origin Walk also asks what changes around it.

Useful reusable questions include:

~~~text
RELATIONAL CONTEXT
  Who depends on this?
  What does this depend on?
  Who produces the truth it consumes?
  Who consumes the truth it produces?
  Which siblings solve related pressures?
  Which connections appear or disappear because it exists?
  Does it coordinate owners or accidentally absorb their truth?

ABSENCE TEST
  If this did not exist, what breaks, duplicates, fragments or becomes ownerless?

COLLAPSE TEST
  If this were merged into a neighbor, what meaning or rightful ownership would be lost?

BYPASS TEST
  If consumers go around this, what do they have to reinvent?
  Does the bypass recreate duplicated interpretation, state, recovery or ownership?

DUPLICATION TEST
  Who else already performs this job?

SUBSTITUTION TEST
  If another mechanism replaced this, would the same human meaning and invariants survive?

SCALE TEST
  With 2 / 20 / 2,000 consumers or children, what multiplies?

FAILURE TEST
  If this fails, what becomes unavailable, stale, ambiguous or unrecoverable?

EVOLUTION TEST
  When one child or target changes, what else must change?
~~~

The answer to one question may expose a new Problem. Re-enter the same question grammar rather than
inventing an unrelated process.

### Standardization and architecture re-entry

A solution that works for one specimen may generate new problems when it becomes the standard.

Before standardizing a reusable mechanism, ask:

~~~text
What new dependencies does this standard create?
Who owns the standard?
Who owns the truths underneath it?
How many synchronization / recovery / interpretation paths now exist?
Does every additional consumer make debugging harder or easier?
What is the blast radius when the standard fails?
Can a fresh maintainer locate the responsible owner without historical context?
~~~

If new pressure appears, perform **Architecture Re-entry**:

~~~text
proposed reusable solution
-> treat the solution itself as new design terrain
-> run the same Problem / Solution Consideration Grammar again
-> refine / converge without discarding unaffected truth
~~~

This recursion is intentional. The Bypass Test may reveal that bypassing the solution recreates the
original problem; the Standardization Test may then reveal that making the solution universal creates new
debugging, ownership or failure pressures. Those new pressures are not exceptions to the Walk: the
solution itself becomes the next subject of the same reasoning method.

~~~text
Problem P
-> Solution X
-> assume X becomes standard
-> new pressure P2 appears
-> Architecture Re-entry on X
-> refine X or its boundary
~~~

### Diagnostic legibility and Ownership Trace

Good reuse should make a system easier to understand and debug, not merely easier to construct.

~~~text
GOOD REUSE
  = easier to build
  + easier to understand
  + easier to debug
  + easier to evolve
  + fewer independent truths to manage
~~~

A standardized path should preserve an **Ownership Trace**:

~~~text
observed result / failure
        ^
platform primitive
        ^
target realization
        ^
semantic mapping
        ^
Origin relationship / state
        ^
human intention / originating cause
~~~

At every boundary, it should remain possible to answer:

~~~text
what semantic request/state is this?
where did it originate?
who currently owns that truth?
which boundary failed?
what did not fail?
who may correct it?
~~~

An abstraction that hides these answers is not mature enough merely because it reduces call-site code.

### Sequencing semantics — one human move may contain ordered semantic moves

A human may experience one action while the architecture correctly represents several ordered semantic
moves.

~~~text
ONE HUMAN MOVE
!= ONE UNDIFFERENTIATED TECHNICAL OPERATION
~~~

The design question becomes:

> What are the meaningful moves inside the one move, and which truth must be prepared before another
> operation can safely consume it?

This is **sequencing semantics**. The sequence should follow semantic dependency rather than convenience
of one target API.

### Semantic Sequence — working term, not yet a schema

The current working term for the ordered semantic dependencies inside one lived action is **Semantic
Sequence**:

> the ordered semantic dependencies required to faithfully resolve one human intention.

This is a reasoning/projection concept today, not yet an independently managed object, registry or wire
schema.

Before formalizing sequence language, pressure it with at least three different shapes:

~~~text
SPECIMEN A — direct navigation
  human: open Debug Menu
  semantic:
    DebugMenuEntryControl
    -> NavigateTo(screen.debug-menu)

  no prerequisite application/domain state is required

SPECIMEN B — state preparation then presentation
  human: choose/open something whose current state must be available at the destination
  semantic:
    originating choice/event
    -> establish current truth through rightful Relay/state owner
    -> dependent state becomes current
    -> NavigateTo(destination) when presentation movement is required
    -> destination consumes dependency

SPECIMEN C — state change without navigation
  human: choose Dark
  semantic:
    Select(ThemeMode.Dark)
    -> ThemeMode becomes Dark
    -> application appearance reflects Dark
~~~

The common pressure may become:

~~~text
human cause
-> prerequisite semantic transition(s)
-> dependent consequence(s)
~~~

but the differences matter. Sequencing must not become synonymous with navigation or force a preparation
step where none exists.

### Sequence should not become another synchronized truth

If VexBoard later visualizes a Semantic Sequence, prefer deriving it from authoritative semantic
relationships, dependency/order constraints and provenance rather than requiring humans or targets to
maintain a second sequence record.

~~~text
authoritative semantic relationships
+ dependencies / order constraints
+ provenance
-> sequence projection

not

Origin relationships
+ separately maintained sequence truth
+ separately maintained target flow truth
~~~

Otherwise sequencing would recreate the duplicated-state/currentness problem it is meant to expose.

### Navigation is not semantic-state transport

A lived predecessor design carried information as navigation parameters:

~~~text
navigateTo(nextScreen, params)
-> destination extracts params
~~~

With several callers, the destination could observe the value while losing important causal truth:

~~~text
Where did the value originate?
Why is it current?
Who owns it?
Which state transition produced it?
What arrived before it?
Can recreation / deep-link / another caller recover the same truth?
~~~

The current architectural pressure is therefore:

~~~text
Navigation
  owns destination/presentation movement

ConvergenceRelay / rightful semantic owner
  owns semantic state propagation
  + source of truth
  + provenance
  + dependency
  + sequence/currentness

NAVIGATION
!= ARBITRARY STATE TRANSPORT
~~~

For state-bearing flows, prefer:

~~~text
prepare / establish semantic truth
-> converge through the rightful Relay/state owner
-> dependent Screen/consumer observes that truth
-> NavigateTo(ScreenId) when presentation movement is actually required
~~~

rather than:

~~~text
NavigateTo(ScreenId, caller-owned-state-payload)
~~~

This does not make every navigation state-driven. A direct navigation edge remains direct when movement
to another destination is the complete meaning:

~~~text
DebugMenuEntryControl
-> NavigateTo(screen.debug-menu)
~~~

The stronger rule is that navigation should not become an accidental courier/source owner merely because
one platform API makes parameter forwarding convenient.

If an argument seems necessary, pressure-test whether it identifies **which semantic destination instance**
or whether it is actually application/domain state that belongs behind a traceable dependency. That
distinction remains an open specimen question rather than a universal ban on every argument.

### Sequencing / provenance example for ConvergenceRelay

The value of ConvergenceRelay is not merely "sharing data." The relevant lived pressure is:

~~~text
many callers
-> each forwards state while navigating
-> destination has several implicit arrival contracts
-> source/provenance becomes caller-dependent
-> debugging requires searching every caller
-> recreation/re-entry must reconstruct caller history
~~~

Convergence changes that shape:

~~~text
originating semantic cause
-> state transition through rightful Relay
-> Relay preserves source / dependency / sequence / currentness
-> destination consumes the Relay dependency
-> navigation/presentation occurs as a separate semantic consequence when needed
~~~

The Bypass Test demonstrates why the Relay boundary matters: bypassing it forces callers to recreate
state transport, provenance and destination coupling independently.

### Unspecified design ambiguity — Default Design Intention

A human request may establish product meaning and required capabilities without specifying visual form,
positioning or responsive behavior.

That must not make target construction creative/random by default.

The current working term is **Default Design Intention**:

> a deterministic reusable design choice used when explicit product/design intent is absent, derived from
> already-earned semantic meaning plus reusable presentation/constraint rules, and replaceable by later
> explicit design without reminting unaffected semantic identities.

The precedence is:

~~~text
explicit human / accepted product design
  > accepted feature-specific design
  > reusable Default Design Intention
  > target-native implementation mechanics
~~~

~~~text
DESIGN UNSPECIFIED
!= DESIGN RANDOM

DEFAULT DESIGN INTENTION
!= SEMANTIC MEANING
!= TARGET TEMPLATE
!= PERMANENT FINAL DESIGN
~~~

Origin meaning answers what/why. The Design lens answers intended form, composition, positioning and
constraints. A target template may repeat how an already-resolved design is constructed; it does not get
to invent that design independently.

If later explicit design replaces a default, preserve the semantic identities and record the design
refinement rather than treating the earlier default as immutable product truth.

### Default form resolution — semantic relationship and value structure before cardinality

A Control's semantic relationship must be known before default form is selected.

The earlier starting heuristic "two values -> Toggle" was too coarse. The current rule is:

~~~text
semantic relationship
+ value structure
+ symmetry / asymmetry
+ visibility / comparison need
+ available design space
-> default form

CARDINALITY
  informs form

CARDINALITY
  does not determine form by itself
~~~

Current reusable tendencies:

~~~text
asymmetric enable/disable-like property
  one condition is naturally expressed as active/inactive
  -> Toggle may be the strongest default

small set of named peer values
  each value carries first-class meaning
  comparison / visibility is useful
  -> visible exclusive choice group is the strongest default

larger value set / long labels / constrained space
  -> compact Selector / Dropdown may become the stronger default

explicit product/design pressure
  -> may choose a different admitted form
~~~

The design form must preserve the semantic relationship. A target-native Toggle, segmented control, radio
group, chips, Dropdown or another widget remains implementation/presentation mechanics underneath that
portable intent.

### ThemeMode default form — preserve peer values visibly

The current ThemeMode specimen supplies concrete pressure:

~~~text
ThemeMode
  Light
  Dark

relationship
  Select(explicit value)

properties
  both values are named peers
  neither is semantically "the enabled state"
~~~

Representing that by default as:

~~~text
Dark Mode
  Off / On
~~~

would reintroduce the asymmetry already removed from semantic meaning:

~~~text
Off -> Light
On  -> Dark
~~~

The stronger Default Design Intention is therefore:

~~~text
Theme
  [ Light ] [ Dark ]

portable intent:
  show the admitted peer values
  show exactly one current selection
  selecting a value means Select(ThemeMode.<value>)
~~~

This is a **visible exclusive choice group**, not a mandate for one platform widget class.

The default is intentionally extensible:

~~~text
Light / Dark
-> visible two-choice group

later Light / Dark / System
-> visible three-choice group may still satisfy the same design intent

later many values / long labels / constrained width
-> compact selector may become the stronger default form
-> semantic operation remains Select
~~~

Thus value-set growth first pressures **presentation**, not semantic-operation migration.

The invariant is that all targets preserve the same choice meaning and current-selection legibility;
familiar target-native rendering mechanics remain underneath the selected portable design form.

### Default screen composition — deterministic growth instead of random positioning

For a settings/debug-style destination whose children are independent row-like interactions and no
different composition is authored, the current default candidate is:

~~~text
Screen content
  -> one ordered vertical flow
  -> children presented as stacked rows / bounded sections
  -> semantic/source order determines initial sibling order
  -> future admitted children can be inserted without inventing absolute coordinates
~~~

This is a **default design candidate**, not a law that every Screen is a list. A game, canvas, dashboard,
media surface or deliberately spatial composition may earn a different design.

The important ambiguity rule is:

~~~text
NO EXPLICIT POSITIONING
-> USE THE ACCEPTED DEFAULT COMPOSITION RULE

not

NO EXPLICIT POSITIONING
-> GENERATE NEW POSITIONING BY TASTE EACH TIME
~~~

### Reachability is the invariant; scrolling is the default overflow mechanism

The deeper requirement is not "every Screen must scroll." It is:

> Every admitted child that belongs to the experience should remain perceptibly reachable across supported
> viewport variation unless the design explicitly intends a different containment/paging/clipping behavior.

For vertically growing row composition, the default realization is therefore a scroll-capable content
region.

~~~text
CONTENT REACHABILITY
  = design invariant

SCROLL
  = default overflow mechanism when content can exceed the available viewport

SCROLL LOCK / NON-SCROLLING SURFACE
  = explicit design constraint when the product meaning requires it
~~~

The scroll owner should be the smallest meaningful container that owns the overflow:

~~~text
full Screen content grows
  -> Screen content region may scroll

fixed header + growing body
  -> body may scroll while header remains fixed

bounded subregion grows
  -> that region may scroll

game / canvas / deliberately fixed viewport
  -> no scrolling when that is explicit design meaning
~~~

This avoids both failure modes:

~~~text
"everything scrolls"
  -> ignores deliberate fixed/spatial design

"nothing scrolls unless someone remembered to ask"
  -> loses content on smaller/different form factors
~~~

The reusable design principle is therefore:

~~~text
viewport differences
-> preserve content reachability

default overflow
-> scrolling at the rightful container

intentional non-scroll
-> explicit constraint with a reason
~~~

### Design defaults must survive the same Origin Walk questions

A default is a proposed reusable solution, so Standardization / Architecture Re-entry applies to it too.

Before making a default broadly reusable, ask:

~~~text
What ambiguity does this default remove?
What cases does it solve?
What product meanings does it accidentally constrain?
What happens when 2 / 20 / 200 children exist?
Can a later explicit design replace it without semantic migration?
Does it improve consistency/debuggability across targets?
Does it create another independent design truth that targets must synchronize?
~~~

A good default should reduce ambiguous design decisions while remaining visibly overridable and
source-traceable.

### Origin Scope Eligibility / Exclusion — earn the coordinate and earn the opposite

The current rule is not "nouns get Origin."

~~~text
Origin scope
  != importance marker
  != reusable-noun marker
  != identity marker
  != noun suffix

Origin scope
  = canonical reusable definition role
    from which realizations / projections may descend
~~~

A semantic thing earns an **independent coordinate in Origin scope** when canonical ownership is materially
needed. Relevant pressures are:

~~~text
CANONICALITY
  one authoritative reusable definition is required

INDEPENDENCE
  an existing parent cannot completely and truthfully own the definition

REALIZATION / PROJECTION PRESSURE
  multiple targets / consumers / projections must descend from the same meaning

EVOLUTION
  duplicating the definition would allow semantic drift as the thing evolves

TRACEABILITY
  consumers need to traverse back to this object as the owner of the meaning
~~~

These are reasoning pressures, not a mechanical checkbox gate.

Earn the opposite too. Before creating an independent Origin-scope coordinate, ask:

~~~text
Can the rightful parent completely own this meaning?
Is this only a value/member of an already-owned domain?
Is this a relationship / verb rather than an independently defined thing?
Is this a runtime occurrence rather than a reusable definition?
Is this target/platform mechanics?
Is this only a realization / projection / adapter / scaffold?
Would another canonical coordinate add ownership/currentness burden
without removing greater duplication or drift?
~~~

If removing the proposed independent coordinate loses no required canonicality, reuse, traceability or
independent evolution, do not create it.

### Default Before Binary

Two currently admitted values do not by themselves justify Boolean/binary semantics.

Before treating a state domain as binary, ask:

~~~text
1. What are the named semantic states?

2. What is the default selection when no prior/current user choice exists?

3. Is "default" itself a selectable semantic state,
   or is it an initialization / fallback / inheritance policy?

4. Are both states peer meanings,
   or is one merely represented as "not the other"?

5. Can a future admitted value be added without changing
   the human-intentional operation or remapping existing state identities?
~~~

Current principle:

~~~text
CONSIDER DEFAULT STATE / DEFAULT-SELECTION POLICY
BEFORE
COLLAPSING A TWO-VALUED DOMAIN INTO BINARY REPRESENTATION

CURRENTLY TWO VALUES
!= BOOLEAN SEMANTICS

DEFAULT SELECTION
!= STATE IDENTITY

DEFAULT
!= FIRST ENUM VALUE
!= FALSE BRANCH
!= PRIMARY merely because it appears first
~~~

For the current specimen:

~~~text
ThemeMode.Light
ThemeMode.Dark
~~~

remain the strongest intrinsic state names because they describe the modes themselves.

`Primary` / `Secondary` are relative roles unless product meaning explicitly defines themes by those
identities. Changing which mode is preferred/default should not require renaming the semantic state.

If product pressure establishes Light as the initial/default mode, represent that separately:

~~~text
ThemeMode values
  Light
  Dark

default ThemeMode
  Light
~~~

That default-selection statement remains open until grounded product evidence earns it.

If a future product adds a true selectable mode such as `System` / `FollowSystem`, that is a new
ThemeMode value, not merely a change to default policy.

rather than `Toggle`.

~~~text
-> Select continues to work

-> add another selectable value
-> no semantic operation migration required
~~~

A Toggle may still realize two-state behavior in a target or explicit design, but it is downstream of the

### Default selection — domain, initialization and recovery are different owners

The current target evidence shows:

~~~text

-> VexLifeSession.darkTheme changes
~~~

The semantic pressure can still resolve the owner of default-selection policy.

~~~text

  defines what the admitted values mean

current ThemeMode
  is application runtime state

  decides which ThemeMode becomes current
  when no more authoritative current/recovered selection exists
~~~

~~~text
    admitted values
    value meaning
    reusable domain evolution

  owns:
    how an initial ThemeMode is resolved
~~~

**Currentness:** `CURRENT_WORKING_MODEL`. This section supersedes older wording in this file where the
same responsibility was described through `Persist`, `Preserve`, `Recover`, `Present`,
`Remembered`, `Found`, `Stale`, `Interrupted`, `Superseded`, or `Committed` language.
Those earlier episodes remain useful causal history; they are not the preferred current vocabulary.

The Walk has now crossed one complete circuit:

~~~text
human Control
-> State-dependent Act
-> Behavior
-> Effect / async execution
-> durable Family storage

-> CURRENT semantic State

~~~

### ThemeMode State

The current State vocabulary is:

~~~text
ThemeMode
  NOT_SET
  Light
  Dark
~~~

`NOT_SET` is a real semantic State because it can change Behavior and Projection. It is not a nullable
implementation accident and it is not silently equal to Light, Dark, or a default.

~~~text
NOT_SET
!= null
!= Failure
!= default ThemeMode
!= ThemeMode.System
~~~

A future reusable target representation may provide `NOT_SET` through foundation State machinery rather
than manually redeclaring it in every Family, but the exact Kotlin/source form remains downstream.

### FamilyStore — minimum durable responsibility

The current candidate is:

~~~text
FamilyStore<Family>

  ObservableState
  Get()
  Save(State)
  Forget()
~~~

For ThemeMode:

~~~text
FamilyStore<ThemeMode>

  ObservableState
  Get()
  Save(ThemeMode.<State>)
  Forget()
~~~

The meanings are deliberately small:

~~~text
Save(State)
  make this Family State durable

Get()
  immutable snapshot of the same stored truth

ObservableState
  ongoing observation of the same stored truth

Forget()
  make the durable Family State NOT_SET
~~~

`Get()` and `ObservableState` are two access forms over one stored truth; they must not become two
independent backing truths.

`Update` is deliberately held. Ordinary form/draft mutation can construct a new immutable State and
`Save` it. A generic atomic read-modify-write operation is earned only when a real consumer needs that
responsibility and no stronger domain verb owns it.

### Current State remains semantic, not storage-owned

The SCAE/current State owner and FamilyStore answer different questions:

~~~text
CURRENT semantic State
  what is true now for Behavior / Projection

FamilyStore durable State
  what has been saved for continuity
~~~

Therefore temporary divergence is legitimate:

~~~text
CURRENT ThemeMode = Dark
stored ThemeMode  = Light

while Save(Dark) is still completing
~~~

The UI does not observe FamilyStore directly.

~~~text
FamilyStore.ObservableState
-> Connection / reconciliation boundary
-> admit<State>() when earned
-> CURRENT semantic State
-> Projection
-> UI
~~~

Storage observation is reality input; it is not itself a UI decision.

### SCAE two-scope async model

The Walk now uses two temporal scopes.

Immediate SCAE disposition:

~~~text
on(...)
  .stay()

or

on(...)
  .admit<State>()
~~~

`.stay()` means no immediate State transition at this decision point. It does not mean the Effect ended.

`.admit<State>()` means this State is admitted immediately at this decision point.

Later async result consequence:

~~~text
begin(...) {
  operation(...)
    .results {
      Success {
        admit<State>()   // only when this later result changes State
      }

      Failure {
        // no admit => no additional State consequence
      }
    }
}
~~~

A later `admit<State>()` is a new State emission back into the rightful State owner, not a second
return from the original `on(...)`.

A result branch does not need a redundant `stay()` merely to say that no later State change occurs.

### Save result surface

The current common operation-result vocabulary is intentionally:

~~~text
Success
Failure
~~~

Do not promote cancellation/interruption/currentness causes into peer semantic result branches unless a
real consumer needs different Behavior for them.

If pending execution is replaced or cancelled **before `Save` begins**, then `Save` produced no result.
That is execution/lifetime detail, not `Save Failure`.

### begin execution modes

Repeated async episodes have now earned two visible execution relationships:

~~~text
begin(mode = Replaceable) { ... }

begin(mode = Sequenced) { ... }
~~~

`Replaceable`:

~~~text
a newer same-lane episode
may replace older pending/cancellable work
when only the newest intended outcome matters
~~~

`Sequenced`:

~~~text
every accepted episode matters
and must retain execution order
~~~

These are not low-level coroutine/thread flags:

~~~text
Replaceable != transaction rollback
Sequenced  != database transaction
shared lane != shared OS thread
~~~

Only these two modes are currently earned. `Concurrent` or other modes remain held until a real consumer
requires them.

### Family identity supplies the execution lane

For FamilyStore operations:

~~~text
SAME FAMILY
-> SAME FamilyStore<Family>
-> SAME execution lane
~~~

Source-code location does not create another lane.

Thus:

~~~text
state<ThemeMode.Light>
  -> Save(ThemeMode.Dark)

state<ThemeMode.Dark>
  -> Save(ThemeMode.Light)

Forget(ThemeMode)
~~~

all coordinate through the same ThemeMode FamilyStore lane.

The `begin(mode = ...)` choice remains authored visibly at the Behavior episode. Different State paths may
intentionally choose different modes on the same lane.

Current mixed-mode rule candidate:

~~~text
existing Replaceable pending work
+ newer same-lane work
-> existing pending work may be replaced

existing Sequenced work
+ newer same-lane work
-> existing work remains
-> newer work waits behind it
~~~

Do not mint `queueId`, `jobId`, `coroutineId`, or another execution identity for this common case.

### Immediate and durability-gated forms

Immediate/live ThemeMode:

~~~text
state<ThemeMode.Light> {
  on(
    act = SelectDark,

    effect = begin(mode = Replaceable) {
      Save(ThemeMode, ThemeMode.Dark)
        .results {
          Success { }
          Failure { }
        }
    }
  )
  .admit<ThemeMode.Dark>()
}
~~~

Human reading:

~~~text
Dark becomes CURRENT now.
Save Dark asynchronously.
A newer ThemeMode save may replace pending replaceable work.
The Save result does not itself change ThemeMode.
~~~

Durability-gated form when a later specimen requires it:

~~~text
state<SomeState> {
  on(
    act = CommitNext,

    effect = begin(mode = Sequenced) {
      Save(SomeFamily, NextState)
        .results {
          Success {
            admit<NextState>()
          }

          Failure {
          }
        }
    }
  )
  .stay()
}
~~~

Human reading:

~~~text
stay in the current State now
-> perform the required Save
-> only Success emits the later admission
~~~

Optimistic rollback remains an advanced explicit recipe rather than part of the ordinary Save grammar,
because a late Failure cannot blindly restore an old State after newer semantic activity.

### NOT_SET + System appearance — bounded convergence

ThemeMode now has two independently changing inputs to effective State:

~~~text
stored ThemeMode override
+
System appearance
-> effective ThemeMode
~~~

Current law:

~~~text

-> effective Light

stored Dark
-> effective Dark

stored NOT_SET
+ System Light
-> effective Light

stored NOT_SET
+ System Dark
-> effective Dark
~~~

Therefore:

~~~text

-> saved override governs

saved override = NOT_SET
-> mapped System appearance governs
~~~

The FamilyStore may remain `NOT_SET` while CURRENT semantic ThemeMode is Light or Dark.

Example:

~~~text

System appearance = Dark
-> effective ThemeMode = Dark
-> admit<ThemeMode.Dark>()
-> Projection / UI renders Dark

FamilyStore remains NOT_SET
~~~

While the stored override remains `NOT_SET`, later System appearance changes may produce another
effective ThemeMode admission.

An explicit human selection:

~~~text
SelectDark
-> admit<ThemeMode.Dark>()
+ Save(ThemeMode.Dark)
~~~

creates a durable override, after which System appearance no longer governs effective ThemeMode.

`Forget(ThemeMode)` returns durable truth to `NOT_SET`; System appearance then governs again.

This relationship now has genuine Convergence pressure because multiple independently changing truths
produce one effective ThemeMode. The implementation may be a simple `when`/switch; Convergence is the
canonical owner of that relationship, not a ban on ordinary target code.

Exact promotion to a canonical ThemeMode ConvergenceRelay remains contingent on grounding the reusable
SystemAppearance State owner. Do not create a Relay merely because a switch statement exists.

## Canonical schema pressure — minimum evolution exposed by ThemeMode

**Currentness:** `CURRENT_WORKING_SCHEMA_PRESSURE`, not accepted VexLife schema.

The completed ThemeMode circuit does not justify a giant new framework. It does expose two concrete gaps in
the current portable Behavior v1 representation.

### Gap 1 — admission must belong to the relationship decision, not the Effect identity

Current Behavior v1 binds each Effect identity to one `admittedStateRef`.

That works for the existing VexStream specimen because each admitted Effect and immediate State kind happen
to align.

ThemeMode now proves a stronger rule:

~~~text
same Effect intention
may participate in:

IMMEDIATE
  on(...).admit<Next>()
  + Save(Next) asynchronously

DURABILITY-GATED
  on(...).stay()
  + Save(Next)
  + Success { admit<Next>() }
~~~

Therefore:

~~~text
EFFECT IDENTITY
!= UNIVERSAL OWNER OF ADMITTED STATE
~~~

The State disposition belongs to the exact relationship/decision point where it occurs.

Minimum pressure for a future portable Behavior revision:

~~~text
law row
  immediate disposition:
    STAY
    or ADMIT(StateRef)

async result branch
  optional later disposition:
    ADMIT(StateRef)
    or no State consequence
~~~

Do not change canonical v1 until repository-local lifecycle/orientation and compatibility impact are
grounded.

### Gap 2 — convergence is not a State selector or a Cartesian Behavior State

The Universal Blueprint documentation already has a multi-source `observeState(sources, selector)`
concept. That is useful read/projection language, but ThemeMode now needs a relationship whose output is
semantic State that may feed Behavior again:

~~~text
stored ThemeMode override
+
SystemAppearance State
-> effective ThemeMode State
~~~

Using a presentation/read selector as the owner would collapse:

~~~text
PROJECTION / READ CLASSIFICATION
with
SEMANTIC STATE RELATIONSHIP
~~~

Flattening the inputs into one synthetic Behavior State would instead collapse independent ownership.

Therefore the current pressure favors a bounded convergence contract/representation that preserves:

~~~text
independent input State identities
one named relational owner
deterministic output State
re-evaluation when any admitted input changes
no cross-Family Effect bypass
~~~

The exact JSON/schema/API is intentionally OPEN.

### FamilyStore representation remains a separate question

The Walk has earned the responsibility:

~~~text
FamilyStore<Family>
  ObservableState
  Get()
  Save(State)
  Forget()
~~~

It has not yet earned a universal JSON registry merely because the responsibility has a name.

Before adding a canonical FamilyStore schema, ask which canonical consumer actually needs to inspect,
generate, validate or map that contract. If target construction can derive the store boundary from the
portable Effect / State / Connection contract without losing truth, do not add another registry.

### Current schema-design priority

The next canonical design pass should therefore pressure, in this order:

~~~text
1. relationship-owned immediate State disposition
2. optional later State admission from async result
3. bounded multi-State convergence representation
4. only then whether FamilyStore needs independent canonical registry identity
~~~

This ordering preserves the semantic circuit while minimizing new source surface.
