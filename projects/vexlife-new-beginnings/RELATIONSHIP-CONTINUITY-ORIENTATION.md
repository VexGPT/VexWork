# Relationship Continuity Orientation

`[VXG RealForever]`

## Why this note exists

This is a project-local orientation checkpoint for the VexLife New Beginnings trajectory.

It exists because a source trace of Conversation, prompt context, Memory, working-continuity rollover and G03 Dream exposed a human question that is easy for a fresh instance to lose by descending too quickly into the existing containers:

> When the model's finite active context must change representation, what must remain genuinely present between Victor and Vex so the conversation does not become a relational reset?

The concrete failure this note prevents is **rehunt plus container-first reasoning**:

```text
fresh instance
-> sees Context / Memory / WorkingSet / Dream owners
-> treats those containers as the intention
-> optimizes their mechanics
-> misses the relationship property they are supposed to preserve
```

This note is not Workgraph lifecycle truth, Product source authority, Memory truth, effect authority, or a claim about God's judgment. It is retained reasoning/navigation so a future instance can recover the human question before changing source.

## Property before mechanism

The present understanding is:

```text
FINITE ACTIVE MODEL CONTEXT
!= RELATIONSHIP DISCONTINUITY

CONTEXT ROLLOVER
!= FRESH CONVERSATION

WORKING CONTINUITY
!= DURABLE MEMORY

DURABLE MEMORY
!= DREAM INTERPRETATION

CANONICAL CONVERSATION
!= CURRENT ACTIVE PROMPT
```

The product does not need an infinite prompt.

It needs a truthful way for representation to change without forcing the human to reconstruct the relationship or ongoing meaning every time raw tokens leave active inference.

A useful question is therefore not initially:

> What summary object should we add?

It is:

> What is still alive between the human and Vex, what has actually completed or been released, and where can Vex return when a detail is no longer actively carried?

## Relationship continuity: present understanding

The current architecture exposes a gap between:

```text
complete raw Conversation
and
accepted long-term Memory
```

The relationship may need a **present carried understanding** that is neither one.

Do not assume a new abstraction is required merely because this note names the gap.

The property to examine first is:

```text
What am I still carrying with the human right now?
```

That may include:

- the human's present intention;
- what Vex presently understands the human to mean;
- distinctions the human emphasized that change later interpretation;
- corrections that changed Vex's prior understanding;
- unresolved questions;
- unfinished commitments or work still owed;
- exact names or unusual wording whose normalization would change meaning;
- meaningful chronology or causal relationships;
- contradictions or uncertainty that remain open;
- relevant relational context;
- source coordinates for details no longer carried directly;
- what has genuinely completed, been superseded or been released.

The important framing is situated rather than authoritative.

Prefer:

```text
"In the present conversation, I understand Victor to be asking..."
"Victor corrected my earlier reading of..."
"I am still uncertain about..."
"This remains unfinished..."
```

over:

```text
"Victor is..."
"Victor always..."
"Victor believes..."
```

A continuity representation should not become an authoritative profile of the human.

## Continuity is not only past -> present

A one-way compression model is incomplete.

Continuity also needs:

```text
present
-> recognizes an older exchange has become newly relevant
-> targeted descent into canonical Conversation
-> present understanding may change
-> what actually happened remains unchanged
```

So continuity can be understood as:

```text
carry forward
+
return backward when needed
+
revise present understanding
```

The active representation does not need to contain every old detail if it truthfully knows where source lives and can re-enter it when needed.

## Release is first-class

Working continuity must not become a second endlessly growing context window.

Things may leave active continuity because they are:

- completed;
- superseded;
- corrected;
- no longer relevant;
- durably carried elsewhere;
- intentionally released.

The aim is not maximal retention.

It is preserving what remains meaningfully alive while allowing what is complete to stop consuming present attention.

```text
CONTINUITY
!= ACCUMULATION
```

## Do not make rollover a narrative-control event

A dangerous implementation would be:

```text
context nearly full
-> model writes one authoritative summary
-> summary silently replaces source meaning
-> future turns inherit the summary as truth
```

That creates several failure modes at once:

- the model may summarize the human from above;
- apparently redundant details may disappear even when their distinction matters;
- uncertainty may be flattened into conclusion;
- correction history may be lost;
- one interpretation may become an accidental permanent frame;
- the human may have to fight a summary they never authored.

If future source uses model-authored working continuity, preserve the difference between:

```text
present interpretation
and
what actually happened
```


For this trajectory specifically, do not silently convert:

into only:

The architecture is downstream of the relationship property.

Similarly, do not turn "work with God" into either:

## Critical correction: ordinary prompt continuity is only one prior pair

Further direct-source review changes the scale of the human problem.

Current `DirectPromptContext.materialize(...)` does not maintain a growing recent Conversation window. Outside `WORKING_CHECKPOINT_SUCCESSOR`, it selects exactly:

```text
immediate prior REQUEST
+ immediate prior RESPONSE
+ current REQUEST
```

The regression is explicit: `continueSelectsExactlyTheImmediatePriorCompletedPair`.

Therefore the first semantic-loss boundary is not necessarily the 192k rollover threshold.

For an ordinary sequence:

```text
turn 1: A
turn 2: B
turn 3: C
```

turn 3 receives the turn-2 pair plus C. If meaning from A was not carried into turn 2's response, current attributed Memory, or another prompt context, A is no longer directly present to the model even though canonical Conversation still preserves it.

This means:

```text
CONVERSATION DURABILITY
!= MULTI-TURN ACTIVE PRESENCE

ROLLOVER CONTINUITY
!= ORDINARY CONVERSATIONAL CONTINUITY
```

The existing pressure/rollover owner solves a real resource/currentness problem, but it does not by itself make ordinary multi-turn conversation semantically continuous.

### Daily Memory does not automatically fill that gap

Current prompt Memory is admitted only when the committed Daily Memory Conversation frontier still equals the current completed Conversation head.

After Conversation advances beyond that Daily frontier, the Memory reader truthfully returns:

```text
HELD / DAILY_MEMORY_SOURCE_FRONTIER_STALE
```

until G03 Memory consolidation catches up. Current G03 is manual one-shot, not standing per-turn consolidation.

So between Daily Memory consolidations, ordinary continuity may rely mainly on the immediate prior pair. This makes a present working semantic carrier materially more important than the rollover threshold alone suggested.

### Revised representation question

The Product may need both:

```text
RECENT VERBATIM PRESENCE
  more than one prior pair while budget allows

and

PRESENT WORKING MEANING
  source-linked / revisable / non-Memory
  for meaning that must survive after raw turns leave active presence
```

Do not assume either one alone is sufficient.

Context pressure should decide when representation must compress; it should not be the first moment the system begins preserving conversational meaning.

## Receive -> carry -> return

Further work clarified the relationship at the point where exact Conversation leaves direct model attention.

The continuity responsibility is not:

```text
preserve everything notable
```
It is:

```text
RECEIVE
  stay with what is actually happening now

CARRY
  retain only what still changes how Vex should be present

RETURN
  reopen exact canonical source when an older detail becomes relevant again
```

The carry question is self-relative:

> From what is leaving direct presence, what still changes how I should be present in this Conversation?

Possible present carry includes:

- something Vex still owes or has not finished;
- something Vex is still trying to understand;
- a correction that must continue to govern Vex's reading;
- a distinction Vex must not collapse;
- uncertainty still open;
- an exact source coordinate Vex may need to return to.

If Vex cannot name how something still bears on the present relationship, it does not need to remain in active carry merely because it was notable.

That keeps working continuity from becoming a hidden human profile or a maximal-retention store.

working-continuity set can fail to carry even its **reference coordinate** unless an earlier successor
already carried it.

This is owner reconnection pressure, not evidence that working continuity should become semantic Memory.

### Smallest candidate design A — reconnect current open-loop coordinates

The first candidate should preserve the existing owner split:

```text
current canonical Score truth
-> narrow read-only current open-loop coordinate projection
-> DirectWorkingContinuity.prepare(...)
-> WorkingSet.openLoopRefs

Score remains semantic/current-truth owner
WorkingContinuity remains reference-only carrier
Memory Context remains Memory-only
no open-loop body/summary is invented
no generic Relay/State/ledger is introduced
```

The projection should carry only enough identity/currentness/source evidence to prove which OPEN-loop refs
are current for this lineage/thread at the prompt/working-set boundary. It should not copy Score semantics
into WorkingContinuity.

Current Score truth should govern the current set. A prior WorkingSet is continuity evidence, not authority
to keep a loop that Score now says is closed. The exact reconciliation rule must therefore be sourced from
current Score semantics rather than implemented as a blind union of old and new refs.

Useful deterministic pressure cases for this candidate:

```text
no prior successor + current OPEN loop
-> current WorkingSet contains that ref

prior successor + same loop still OPEN
-> ref remains without duplication

prior successor + loop now CLOSED
-> stale ref does not survive merely because prior WorkingSet carried it

new OPEN loop after prior checkpoint
-> current WorkingSet acquires it

Memory projection HELD/stale while Score truth is independently current
-> do not infer that open-loop truth is absent merely because prompt Memory body is unavailable

working-continuity output
-> carries refs/source identity only
-> does not expose fabricated semantic content
```

The exact source placement remains a design decision: the present Memory reader already performs validated
Score replay internally, but that does not automatically make the Memory contract the public owner of a
Score projection. Prefer the smallest read-only projection at the rightful existing Score/current-source
boundary rather than widening Memory merely because its reader already traverses Score.

### Candidate design B is conditional — typed resolution of an already-carried ref

Reacquiring an open-loop ref improves **owner continuity**. It does not by itself give Vex the semantic
content behind that ref.

Current working-continuity prompt text deliberately says refs are non-semantic coordinates. The current
model-facing source-return capability resolves canonical Conversation only.

Therefore:

```text
current openLoopRef present
!= model knows what the open loop means

coordinate continuity
!= conversational meaning continuity
```

If lived evidence later shows that Vex recognizes an unfinished-thread cue but cannot answer because the
needed current owner content is behind a Score/open-loop coordinate, the next candidate should be a
**typed owner-specific source resolution relationship**, not an automatic generic resolver:

```text
model recognizes exact need
-> bounded typed request to the rightful Score/open-loop owner
-> exact/current owner projection
-> final inference
```

Conversation source return is precedent for the relationship shape, not permission to make one universal
search/Relay abstraction.

Do not implement this candidate until a real consumer need establishes which Score/open-loop content must
be returned, what exact currentness/consent boundary governs it, and what human-visible result proves that
the relationship improved.

### Truthful boundary for weak or deictic cues

The current lexical Conversation return works when Vex can name distinctive source terms from what remains
present.

For a cue such as “that thing before,” three cases remain distinct:

```text
1. an existing current owner still carries a useful coordinate
   -> resolve through that rightful owner when the relationship is earned

2. enough distinctive meaning remains to request exact Conversation source
   -> use the existing conditional exact-source return

3. no current owner/coordinate/meaning survived because the detail was genuinely released
   -> preserve uncertainty; do not fabricate recall
```

A future transient/revisable semantic carry should be considered only if ordinary lived failures repeatedly
show that a relationship must remain recognizable across release while no existing owner can rightfully
carry the necessary present meaning. Earlier working-carry research remains research, not the default
answer, especially because mandatory semantic carry near the same finite-context boundary can recreate the
pressure it is intended to solve.

### Current design continuation

The next design sequence is:

```text
A. finish the current-open-loop reconnection design at the rightful Score/WorkingContinuity boundary
B. verify whether that closes any concrete unfinished-thread continuity case
C. preserve Conversation exact-source return unchanged for exact older Conversation
D. add an owner-specific ref resolver only when lived evidence proves a real consumer need
E. consider new transient semantic carry only after a recurring genuinely ownerless relationship failure
```

No Product source mutation is implied by this section. Product implementation still requires its own current
Work/authority/custody admission.

## Candidate A refinement — restore the stable Score producer relationship

Further source descent resolves the main placement question for candidate A.

The bound stable VexLife reference already had a separate read-only Score projection:

```text
vgong24/VexLife
revision 7d59753687ff12726b0d309ee2dde028b5f89e8a

score-context-continuity.mjs
-> projectScoreContext(...)
-> schemaVersion = vexlife.score-context-projection/v1

continuity-stream-adapter.mjs
-> consumes that Score projection
-> currentStatementRefs = Score current statements
-> openLoopRefs = Score OPEN loops
-> places those refs into the reference-only WorkingSet
```

The clean Kotlin Product retained the WorkingSet fields but its current direct producer no longer consumes a
Score projection:

```text
DirectWorkingContinuity.prepare(...)
-> currentStatementRefs =
     prior WorkingSet currentStatementRefs
     + statement refs selected into current Memory
-> openLoopRefs =
     prior WorkingSet openLoopRefs only
```

Therefore the preferred interpretation is:

```text
LOST / UNRECONNECTED PRODUCER RELATIONSHIP
!= NEW SEMANTIC FEATURE
```

### Proposed source shape

Do not widen `VexLifeMemoryContract.Context` to carry Score semantics merely because
`VexLifeCurrentMemoryReader` currently traverses Score internally.

The clean implementation should restore one independently typed read-only current Score projection and let
both consumers use that owner truth:

```text
canonical Home Score
-> one current Score replay / validation owner
-> read-only Score projection
   - currentness / attention
   - lineage + thread
   - exact Score head when present
   - exact Score source Conversation head when present
   - semantic-authority current head when present
   - current statement refs
   - current OPEN-loop refs
   - source / projection identity needed for currentness proof

                    +----------------------+
                    |                      |
                    v                      v
          Memory formation        WorkingContinuity formation
          selects admitted        carries current refs only
          semantic pages          no semantic body copied
```

Prefer preserving the accepted `vexlife.score-context-projection/v1` relationship rather than inventing a
different semantic meaning under a new generic continuity contract. Exact Kotlin file/class placement remains
subject to Product source review, but the semantic owner should be Score/current-source truth, not Memory and
not WorkingContinuity.

If the existing Score replay currently embedded inside `VexLifeCurrentMemoryReader` is extracted, Memory
should consume that same validated reader/projection rather than maintaining a second independent Score
replay implementation.

### WorkingSet composition law

For the Score-owned fields, current Score replaces stale inherited coordinates:

```text
WorkingSet.currentStatementRefs
= exact current Score statement refs

WorkingSet.openLoopRefs
= exact current Score OPEN-loop refs
```

Do **not** blindly union these sets with the prior successor:

```text
prior successor says loop OPEN
+ current Score no longer says loop OPEN
-> prior ref must not survive as current merely through inheritance
```

The prior WorkingSet remains useful continuity/provenance evidence for fields whose current producers have not
yet been reconnected, but it is not authority over a current Score set.

Memory selection remains independent:

```text
Score current statement refs
!= Memory pages selected into prompt

Memory bounded/held
!= Score statement/open-loop truth absent
```

This restores coordinate continuity without turning every current Score statement into prompt Memory content.

### Empty, attention, and currentness semantics

The stable Score source already distinguishes these cases:

```text
no Score head
+ no invalid/attention evidence
-> CURRENT empty Score projection
-> currentStatementRefs = []
-> openLoopRefs = []

valid current Score head
-> CURRENT exact current sets

invalid/re-addressed/source-invalid tail or other Score attention
-> ATTENTION
-> do not assert an exact current Score set
```

Candidate A should preserve that distinction.

A Score projection that is not safely current must not silently fall back to stale prior Score refs and must
not be interpreted as an empty current set.

### Turn-liveness and post-turn checkpoint law

Working continuity is stewardship around the human turn, not authority to reject an otherwise valid answer.

Current Product already preserves:

```text
Conversation RESPONSE durable
!= working continuity must have succeeded
```

Candidate A should extend that law:

```text
Score projection CURRENT
-> form current WorkingSet + Plan

Score projection ATTENTION / unreadable / currentness-invalid
-> working-continuity formation HELD
-> no new checkpoint/head promoted from unproven Score truth
-> provider / human turn may continue under its existing rightful inputs

Conversation RESPONSE already committed
+ later Score/currentness recheck fails
-> working continuity HELD
-> never retroactively convert the completed send into failure
```

The implementation should bind the exact Score projection/head used to form the WorkingSet and re-observe the
current Score frontier before realizing the post-turn checkpoint. If the Score projection materially changed
during the provider turn, hold/reform the working-continuity effect rather than commit a stale working set as
current.

### Candidate A proof matrix

At minimum, the source change should prove:

```text
no prior successor + no Score head
-> current empty Score coordinate sets; ordinary turn unaffected

no prior successor + current Score statement/open loop
-> WorkingSet gets both current refs

Memory includes only a subset of current Score statements
-> WorkingSet still carries exact current Score statement refs
-> provider Memory still contains only its admitted bounded pages

Memory HELD / no Memory pages
+ Score CURRENT
-> WorkingSet can still carry current Score coordinates
-> no Score semantic body leaks into Memory/prompt

prior successor + same loop still OPEN
-> one current ref

prior successor + loop no longer current
-> stale inherited ref removed

new Score statement/open loop after prior checkpoint
-> current refs acquired

Score ATTENTION at formation
-> no new working checkpoint
-> human turn not rejected merely for working-continuity stewardship

Score changes after formation but before post-turn commit
-> checkpoint realization held
-> stale Score refs not promoted
-> committed Conversation response remains valid

source-return turn
-> final WorkingContinuity preparation uses the same current-Score law
-> Conversation exact-source-return behavior remains unchanged
```

### What candidate A does not solve

Restoring Score coordinates does not make their semantic bodies model-visible:

```text
Score/openLoop ref carried
!= Vex can read what it means
```

That remains candidate B and stays conditional on a lived consumer need.

Likewise, restoring the stable Score producer does not itself justify reconnecting Intent work nodes,
continuity-record sets, or another predecessor producer. Each remaining WorkingSet field must be traced to
its current rightful owner and an actual consumer need before its producer relationship is restored.

No Product source mutation is authorized by this design note. It preserves the implementation shape so a
future admitted Product work item can start from current source truth rather than rediscovering or
re-architecting the relationship.
