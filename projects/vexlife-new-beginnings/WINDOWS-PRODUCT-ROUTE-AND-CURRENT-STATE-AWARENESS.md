[VXG RealForever]

## Status

This is a documentation-only continuity/orientation record inside the existing
project.vexlife.new-beginnings neighborhood.

It does not create a new Project, Work item, WorkState transition, Product implementation authority,
model activation authority, lifecycle effect, provider effect, or generated VexWork consequence.

The future human-facing outcome is provisionally named:

~~~text
VexLife Windows Product Route
~~~

"Windows launcher" is shorthand only. The intended outcome is larger than a script or executable:
a Windows person should eventually reach the same VexLife product relationship through
Windows-native realization.

The Windows Project is not formed yet because current human clarification places one predecessor
foundation first:

~~~text
Mac leading example
    ↓

    +

    ↓

    ↓
accepted platform-independent product relationship
    ↓

    ↓

~~~

This sequencing avoids making today's Mac-specific Heretic/runtime shape the definition of VexLife.

## Human intention

Before VexLife asks a person to Open, Repair, Rebuild, Change model, authorize a download, or later
enter a Windows setup route, show enough current machine and Vex truth for the person to understand:

- what they currently have;
- what VexLife currently uses;
- what the requested operation would require;
- what is already present and reusable;
- what is missing;
- whether the current machine appears capable of carrying the requested realization;
- what will remain preserved.

The human surface should expose truthful scope and limits without becoming another owner of those
truths.

~~~text
CURRENT TRUTH
    ↓
bounded human projection
    ↓
human choice
    ↓
fresh currentness check
    ↓
rightful owner performs effect
    ↓
fresh observation
    ↓
updated human projection
~~~

Permanent:

~~~text
AWARENESS != AUTHORITY

DISPLAYED ELIGIBILITY != RUNTIME QUALIFICATION

MODEL DESCRIPTION != MODEL PERMISSION
MODEL REGISTRATION != MODEL CURRENT
MODEL REGISTRATION != SOLE ADMISSION REQUIREMENT

MODEL BYTES PRESENT != MODEL RUNNABLE
MODEL RUNNABLE != MODEL ACTIVE

USER CHOICE != EFFECT ALREADY PERFORMED

PRE-EFFECT SNAPSHOT != PERMANENT TRUTH
~~~

A model catalog may carry accepted/certified identity and artifact facts. It is a truthful
description/confirmation surface, not an independent reason that the model must or may be selected.

## Decision posture

Consequential architecture choices should not jump directly from a technically convenient pattern to
a conclusion.

Victor's current posture is to make a genuine ask to Holy Father God before consequential
architecture decisions, then test what comes through against current source, lived outcome, and
existing ownership boundaries rather than treating the ask as ritual, methodology, or certification.

No repository statement here claims divine certification of a technical conclusion.

## Current source observations that motivated this record

Current stable VexLife already observes host/resource facts in scripts/initialize-vex.mjs:

~~~text
platform
architecture
Node version
totalMemoryBytes = os.totalmem()
freeDiskBytes    = statfs(Home volume)
NVIDIA evidence
Apple hardware evidence
~~~

Its operational-profile evaluator can hold a route for insufficient system memory, insufficient free
disk, missing NVIDIA evidence, or Apple-chip mismatch.

The ordinary Mac setup surface, however, primarily projects actions and coarse acquisition language
such as "about 15 GiB" rather than the current observed machine/resource vector.

Current VexLife-Prod also has a Mac Heretic host profile that observes exact chip class and total
system memory, while its current Product-owned Heretic path does not yet project one complete
human-facing storage/RAM/operation requirement view.

Therefore the gap is not simply "add more labels to setup." It is:

~~~text
backend truths / exact artifact requirements
        ↓
bounded current-state convergence
        ↓
human awareness before effect
~~~

Current model lineage also already carries multiple MLX model bundles with source-managed:

~~~text
model bundle identity
model profile identity
artifactBindings[]
artifact-set identity
content-set SHA-256
runtime realization ref
~~~

Their physical member shapes differ legitimately. That difference should be carried by the manifest
rather than hard-coded into setup logic.

~~~text
DIFFERENT MEMBER LAYOUT
!= DIFFERENT DOWNLOAD ARCHITECTURE
~~~

The current VexLife-Prod Heretic materializer is still specialized to the 27B artifact/path and is
therefore a concrete patient-zero implementation rather than the final scalable model-materialization
relationship.

## Operation-specific truth

Repair means restore the currently selected realization to a current/healthy state. It does not mean
change the selected model.

Before consent, derive the operation-specific requirement from current observations.

Permanent:

~~~text
REPAIR != MODEL CHANGE

TOTAL MODEL SIZE
!= ADDITIONAL DOWNLOAD REQUIRED
!= TEMPORARY WORKING SPACE REQUIRED
!= CURRENT FREE STORAGE

TOTAL SYSTEM MEMORY
!= CURRENT AVAILABLE MEMORY
!= MODEL DECLARED MINIMUM
!= OBSERVED RUNTIME WORKING SET
~~~

A model already fully present should not be presented as if its total size must be downloaded again.

## Manifest-driven model materialization

The scalable target is that model-specific file shape is data:

~~~text
selected model
→ resolve exact artifact manifest
→ derive model storage coordinate
→ inspect every member
→ reuse exact members
→ acquire missing members only with authority
→ verify size + hash
→ verify whole content-set seal
→ return qualified artifact-set evidence
~~~

Adding a later model should not require a new model-specific downloader merely because it has a
different member count or sharding arrangement.

Conceptually:

~~~text
<Vex Home>/
  models/
    heretic/
      <model-or-bundle identity>/
        <provider revision>/
          <manifest members>
~~~

Exact final placement remains a Product-source decision; this document does not redefine existing
accepted paths by itself.

## Transactional model change

A model change is not:

~~~text
write config
→ hope the model starts
~~~

It is:

~~~text
current active model A
        ↓
human selects model B
        ↓
fresh host observation
        ↓
fresh artifact observation
        ↓
form ModelChangePlan
        ↓
show exact known consequences
        ↓
human authorizes acquisition if required
        ↓
recheck material predicates
        ↓
acquire only missing authorized artifacts
        ↓
verify exact artifacts
        ↓
establish/reuse required runtime
        ↓
qualify B
        ↓
commit B as current model
        ↓
fresh CurrentStateSnapshot
~~~

Critical:

~~~text
ACTIVE MODEL A
REMAINS CURRENT
UNTIL MODEL B IS QUALIFIED
~~~
