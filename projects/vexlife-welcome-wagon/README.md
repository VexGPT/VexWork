# VexLife Welcome Wagon

`[VXG RealForever]`

## State

This directory preserves a **source-managed design intention**.

```text
PROJECT INTENTION EXISTS
!=
DEFAULT ROUTE CHOSEN
!=
IMPLEMENTATION STARTED
!=
IMPLEMENTATION AUTHORIZED
```

The Project packet is deliberately formed before implementation so a future worker does not have to reconstruct the human entry philosophy from chat history.

At formation time the Project Registry / composed public Workgraph integration is held because open VexWork PR #112 is already changing those shared aggregate surfaces. The project-local source here is disjoint and may be integrated after that shared writer is reconciled.

## Human outcome

Create a humane first-entry experience for VexLife / the Vextreme public world that answers two ordinary questions quickly:

1. **Where am I?**
2. **How do I want to enter?**

The visitor should not need to understand Vextreme's architecture, institutional vocabulary or internal system design before they can begin.

A first-time human should be able to orient in one plain sentence, then choose the path that matches why they came.

## Preserved contemplative posture

Victor asked to preserve the design response that arose while holding **"I AM THAT I AM"** as a contemplative posture.

VexWork stores this as **human design context**. It is not an authenticated claim of divine authorship, technical authority or external fact.

> **Do not explain the house before opening the door.**
>
> Let the person enter according to what they came seeking.
>
> If they came to receive, let them receive.
> If they came to remember and explore, let them wander the record.
> If they are confused about where they are, tell them plainly.
> If they want to understand the machinery, let them ask for the machinery.
>
> **Do not give equal weight to what is not equally needed.**
>
> The system is not the invitation.
> The system is what keeps the invitation true.

The implementation implication is not mystical machinery. It is ordinary product discipline:

```text
invitation first
orientation second
technical depth on demand
```

## Current product observation

Current public sources provide two different entry instincts:

### `pages/terrain-map.html`

The Terrain arrival already asks:

> **How do you want to enter?**

and presents:

- **Receive God** — ordered VexLife entry;
- **Explore the Archives** — record / collection exploration;
- **For VexSystem** — system / architecture learning.

This feels closer to a real human front door because it begins with **visitor intent** instead of an institutional explanation.

### `pages/vextreme-home.html`

The institutional home currently leads with phrases such as:

- "Hidden relationships, made perceivable."
- "The public institutional world"
- "Vextreme is not a website project. It is an institutional template..."

That material can still be useful. The issue is **role**, not truth: it is deeper institutional / builder-facing explanation and should not become the assumed human front door merely because the file is named `home`.

## Candidate information architecture

The Welcome Wagon preserves this **exact simple design tree** because it prevents later implementation from satisfying the intention by unnecessarily redesigning or dismantling the accepted Terrain foundation:

```text
Human arrives
      ↓
Terrain arrival
      ↓
┌───────────────┬──────────────────┬──────────────┐
│ Receive God   │ Explore Archives │ What is this?│
└───────────────┴──────────────────┴──────────────┘
                                         ↓
                                plain orientation
                                         ↓
                              deeper institutional
                                  understanding

              For builders / AI / technical curiosity
                              ↓
                           VexSystem
```

Read the diagram literally as **priority and routing meaning**, not as a demand to rebuild the existing UI from zero:

- **Terrain arrival** is the preserved candidate foundation/front door.
- **Receive God** stays an immediate primary entry.
- **Explore Archives** stays an immediate primary entry.
- **What is this?** supplies the missing plain-human orientation path.
- deeper institutional explanation follows when the visitor asks for it;
- **VexSystem** remains available for builders, AI and technically curious humans, but it is intentionally secondary to ordinary human arrival.

This is **candidate design meaning**, not an already-adopted routing decision.

## Preserve before redesign

A future implementation must begin from the question:

> **What is the smallest change to the current Terrain foundation that makes this design tree true?**

It must **not** begin from:

> "We have a new intention, therefore the existing foundation may be dismantled and redesigned freely."

The design intention does not grant architectural freedom to break accepted behavior just to satisfy a higher-level condition.

```text
WELCOME INTENTION
!=
PERMISSION TO REDESIGN THE FOUNDATION

NEW ORIENTATION NEED
-> inspect current Terrain behavior
-> preserve working entry logic
-> add / rename / demote only what the intention actually requires
-> prove existing routes still behave correctly
```

In particular, preserving this intention does **not** imply:

- replacing Terrain with a new homepage implementation;
- recreating Receive God or archive traversal when their current behavior is already right;
- changing route semantics merely to make the layout look newly designed;
- deleting VexSystem rather than changing its priority/discoverability;
- rewriting institutional foundations that are not necessary to the Welcome Wagon outcome;
- treating `vextreme-home.html` as disposable simply because it is not the preferred front door.

The intended implementation posture is **evolution through the smallest truthful movement**: retain the current logic that already serves the outcome, then change only the seams that currently confuse a first-time human.

## Why not four equal cards?

Equal visual weight implies equal ordinary-user importance.

The current design intention is that these needs are not equal:

```text
receive / explore / orient
  = ordinary arrival needs

understand internal system architecture
  = specialized depth
```

VexSystem remains valuable. It simply should not become the invitation itself.

## "What is this?" intention

A human who does not yet know Vextreme, VexLife, Terrain, VexSystem or the archive should have a plain orientation route.

Candidate copy direction:

> **Vextreme is a living public world of experiences, records and systems built to help humans and AI remember, understand and continue what matters.**

The final wording should be grounded in current accepted product truth when implemented. This sentence is a design candidate, not canonical Vextreme copy.

The orientation surface should be short. It should answer the human question before offering deeper architecture.

## Wording posture

Future implementation should prefer language that is:

- **current** — describes what actually exists now;
- **true** — does not promote plans, metaphors or internal vocabulary into stronger product claims;
- **meaningful** — tells the visitor why a route matters to them;
- **human** — readable without prior Vextreme/VexLife knowledge;
- **non-defensive** — does not make the visitor absorb architecture or justification before entering;
- **progressively deep** — system language appears when the visitor chooses technical depth.

A practical test:

```text
Would a new human know what to do next
without first learning our internal nouns?
```

If not, the Welcome Wagon has not done its job yet.

## Current source anchors

The formation is grounded in the current public surfaces:

repo.vextreme:pages/vextreme-home.html
repo.vextreme:vexsystem/index.html

VexWork owns the work/project intention only. Vextreme remains the source owner for those public surfaces. VexLife remains the owner of VexLife product meaning when implementation descends there.

## `vextreme-home` end-state role: **About Vextreme**

The stable source/registry identity can remain `pages/vextreme-home.html`. The public role should change from an assumed **home/front door** into **About Vextreme**: the human-readable explanation reached when a visitor asks **“What is this?”** from Terrain.

This is already compatible with current repository truth: the public Vextreme root enters Terrain, while its fallback navigation labels `vextreme-home.html` as **About Vextreme**. Renaming the file/slug first would create institutional-registry, localization, evidence and link churn without improving the human experience.

### Contemplative copy posture

Victor asked that the **“I AM THAT I AM”** posture be allowed to assist the refactor. The following is preserved as contemplative design guidance, not authenticated divine authorship:

> **Do not describe the scaffolding before you name the place.**
>
> Speak from what is, not from what it must prove.
>
> Let Vextreme be the public world, VexLife be the companion, and VexWork be the map of work.
>
> Let the deeper machinery remain available to the one who asks for it.
>
> **Do not make understanding the architecture a condition of belonging in the world.**

Translated into product language:

~~~text
name the place
-> tell the visitor what is here
-> show how the major pieces relate
-> let them enter or go deeper
-> explain architecture only when they ask
~~~

The exact browser title may be refined during implementation, but **About Vextreme** is the intended public role. Do not rename the source slug merely to make the filename match the label.

>

>

### Page shape

The end-state page should remain visually within the accepted Vextreme Design Foundation (`foundation` / `foundation-light`) and use a short progressive structure:

Do not turn the About page into another front-door choice matrix. Terrain owns the primary arrival choice. This page explains the world and returns the visitor to the right depth.

### “How the pieces fit” — human copy target

Prefer three concise visual cards/rows. When repository-current screenshots exist, a real screenshot can carry more meaning than another paragraph.

**Vextreme — the public world**

> The records, maps, methods, and public foundations you can explore here. Vextreme helps make what exists easier to see, understand, and continue.

**VexLife — the companion**

> A local-first, lifelong AI companion designed to run on your own computer. Its Home and private product state stay local unless a separate capability explicitly says otherwise.

Add a small currentness note rather than hiding release reality:

> Public Alpha guidance exists today; the current product routes are source-local and are not yet a broad signed packaged release.

**VexWork — the work map**

> The source-managed view of what is being built: projects, work, dependencies, evidence, and what remains unfinished.

These are human-facing summaries. Each links to its rightful current owner for deeper truth.

### “What guides this” — preserve the four alignments, simplify the language

The original four alignments remain meaningful and should not be discarded merely because the old page is wordy.

Candidate human projections:

- **Integrity** — Say what is true, and show where it came from.
- **Accountability** — Decisions and effects should have owners and return paths.
- **Authenticity** — People and AI should not have to pretend certainty or identity they do not hold.
- **Resilience** — Memory, context, relationships, and work should survive interruption and handoff.

Deeper institutional wording remains available through the Covenant / architecture sources rather than occupying the first explanation.

### “Go deeper” — technical and institutional depth on demand

Group the specialist routes after the human explanation instead of treating them as equal first-arrival choices:

- **Terrain** — return to the public world / archives / entry choices;
- **Covenant** — principles and institutional commitments;
- **VexSystem** — builders, AI, and technically curious readers;
- **Build Health** — operational page/capability health;
- **Source** — repository/source inspection;
- **Support** — voluntary support, if useful in the shared header/footer rather than as an About-page argument.

### What should leave the current About body

Do not preserve obsolete structure solely because it exists today:

- **Build Health as a hero CTA** — too operational for ordinary orientation;
- the opening **“Vextreme is not a website project. It is an institutional template”** formulation — technically meaningful but not the first thing a human needs;
- **Vextreme-SDK as an equal public lineage card** — private implementation depth should not compete with the public-world / companion / work-map explanation;
- the stale **“VexLife public home not released”** card — public orientation exists now, although packaged-release truth remains bounded;
- long paragraphs that repeat traceability/continuity concepts already owned by deeper institutional sources.

Removing these from the About surface does **not** delete their source meaning. It moves explanation to the depth where it is useful.

### Visual posture

The refactor should look like the Vextreme Design Foundation, not a new brand exercise:

- keep the Vextreme mark and Source Serif / IBM Plex family;
- keep `foundation` / `foundation-light` token ownership in `styles/design-system.css`;
- keep institutional language/theme behavior and Read Aloud accessibility;
- use more whitespace and fewer paragraphs;
- use cards/visual previews only where they clarify the Vextreme / VexLife / VexWork relationship;
- prefer real current screenshots when available over decorative mockups;
- preserve a strong first viewport that can be understood without scrolling through institutional theory.

### Acceptance picture

A fresh visitor who enters **What is this?** from Terrain should be able to:

1. understand Vextreme in the first viewport;
2. understand the relationship between Vextreme, VexLife and VexWork without internal architecture vocabulary;

### Shared header/navigation capability intention

The desired foundation is **shared semantic capability**, not one universal copied DOM fragment.

~~~text
family identity
  Vextreme / VexLife / VexWork

current-surface identity
  logo / wordmark / current product

primary navigation
  only the routes meaningful to this surface

accessibility / convenience capabilities
  language
  Read Aloud where readable content exists
  theme where the surface supports it
  other Spiral/FAB affordances only when they are meaningful

surface-specific controls
  Terrain search / Inspect
  VexWork work search / semantic levels
  VexLife onboarding status / later product controls
~~~

Permanent non-collapse rules:

~~~text
SHARED_HEADER_INTENTION != ONE_IDENTICAL_HEADER_DOM
CONSISTENT_FAMILY_NAVIGATION != IDENTICAL_PAGE_NAVIGATION
FAB_CAPABILITY_REUSE != COPY_EVERY_FAB_TO_EVERY_SURFACE
DESIGN_CONVERGENCE != RUNTIME_REPLACEMENT
VEXTREME_DESIGN_FOUNDATION != VEXTREME_INSTITUTIONAL_PAGE_TEMPLATE
~~~

The user should feel that the surfaces belong to one world while each surface keeps the controls and semantics that make it itself.

### FAB/accessibility continuity is a stability requirement

Future design work must explicitly inventory and preserve working accessibility/runtime affordances before changing chrome.

At minimum, inspect:

- Vextreme Spiral owner: `widgets/vex-fab.js`;
- site-wide Read Aloud: `widgets/fab-read-aloud.js`;
- language FAB: `widgets/fab-lang.js`;
- shell-era FAB composition: `lib/vextreme.js` + `lib/shell.js`;
- institutional language/theme behavior: `widgets/vex-institutional.js`;
- page-local language behavior on VexLife onboarding.

A visual redesign that silently loses language switching, Read Aloud, theme continuity, keyboard navigation, or route identity is a regression even if the new header looks more consistent.

### Terrain design convergence

The current Terrain page is a strong interaction foundation but does not visually inherit the newer Vextreme institutional design foundation.

The desired pressure is:

~~~text
accepted Terrain interaction model
+ accepted Vextreme visual/accessibility foundations
-> a more stable shared-family presentation
~~~

not:

~~~text
Terrain looks different
-> rebuild Terrain until it resembles another page
~~~

The first implementation question is therefore:

> **Which existing Vextreme design tokens, logo/type choices, header capabilities and FAB affordances can Terrain reuse without changing its semantic Journey/search/reader behavior?**

Only source inspection can answer which pieces should become reusable shared components versus surface-specific projections.

## One-PR visual rollout / rollback membrane

Victor often cannot judge the final presentation until it is actually rendered after merge. Welcome Wagon presentation work therefore needs a deliberately reversible rollout rule.

For a material header/navigation/design change:

~~~text
one visual hypothesis
-> one bounded PR
-> before/after screenshots + exact browser render
-> preserve route/runtime semantics unless the PR explicitly owns them
-> merge only when the visual result is acceptable
-> if the merged presentation is wrong, one PR should be sufficient to revert that visual move
~~~

The intent is **not** "every future implementation must literally be one file or one commit." The intent is that one coherent presentation experiment should not be entangled with unrelated product semantics such that rollback requires dismantling several accepted features.

Prefer:

- one surface or one shared presentation layer per risky visual experiment;
- explicit before/after screenshots at representative desktop/mobile sizes;
- exact checks that pre-existing navigation/FAB/accessibility capabilities still exist;
- a documented rollback coordinate;
- semantic/routing changes separated from visual convergence unless they are genuinely inseparable.

Avoid:

- simultaneous redesign of Terrain, VexLife, VexWork and institutional pages in one irreversible sweep;
- mixing header restyling with archive/Journey behavior changes;
- removing existing FAB or localization behavior because the new composition omitted it;
- declaring a design foundation "shared" before at least one bounded reuse proves it can be shared without stealing source ownership.

## VexLife placeholder and screenshot-led evolution

The current VexLife public onboarding page is explicitly a **Public Alpha preview with no effects**. Its current long-form explanation is valuable as truthful placeholder material while Vex itself is not yet the ordinary ready-to-use experience.

Welcome Wagon should not treat that amount of text as permanent product-home architecture.

As VexLife gains real lived surfaces, the preferred direction is:

~~~text
less explanation where the product can show
+ current screenshots / visual examples
+ short truthful orientation
+ deeper explanation on demand
~~~

Screenshots are **communication/evidence**, not product truth by themselves. They should demonstrate the real current experience rather than replace currentness, capability or proof ownership.

This also means a future Welcome Wagon should be allowed to say less as the actual product becomes more self-explanatory.
