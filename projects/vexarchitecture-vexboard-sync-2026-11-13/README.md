## End-to-end feature invariant

Screen Lens is a hub-space projection over source truth. It must not become a second feature model or architecture registry.

An end-to-end feature is **not** "every class beneath a Screen", one mandatory linear pipeline, or one giant integration test. It is the source-proven causal/lived feature slice whose ownership remains intelligible from the human/product intention through whatever reality actually changes and back to what the human can experience.

When source earns the full loop, the useful causal spine is:

```text
human / product intention
    ↓
Control + exact CURRENT State
    ↓
Family / rightful semantic decision
    ↓
Act
├─ admitted semantic State, when earned
└─ Effect, when concrete realization is needed
    ↓
bound Method / concrete realization
    ↓
Execution custody, when earned
    ↓
Store / provider / platform / Partner participation
    ↓
independently-owned reality
    ↓
rightful observation + reconciliation
    ↓
already-semantic State / relationship truth
    ↓
Family.observe(...) or the rightful semantic owner
    ↓
Projection / DisplayState
    ↓
concrete presentation meaning
    ↓
platform manifestation
    ↓
human experience
```

The loop is conditional, not ceremonial:

```text
Partner
    only when independently-owned external participation earns
    Source / Signal / Connection / Observation semantics

Relay / convergence
    only when independently-owned truths must become new relationship truth

Service / sustained realization
    only when concrete behavior must outlive the initiating UI/caller
    while semantic truth remains elsewhere

Widget / other human surface
    manifestation of already-owned truth
    != a second semantic owner

Dependency / construction
Logger / chronology
Forensics / provenance
    orthogonal relationships
    != mandatory sequential stages
```

Therefore:

```text
END_TO_END != TRACE_EVERY_CLASS
END_TO_END != FORCE_EVERY_ARCHITECTURAL_NOUN
END_TO_END != ONE_GIANT_TEST
END_TO_END != STORE_MUST_ALWAYS_HAVE_MORE_DEPTH

SOURCE-PROVEN RETURN EXISTS
+ LENS TERMINATES BEFORE IT
-> PROJECTION GAP

SOURCE-PROVEN RELATIONSHIP IS ALREADY EXTRACTED
+ BOARD FACE HIDES / COLLAPSES IT
-> PROJECTION GAP

SOURCE TRUTHFULLY STOPS
-> RIGHTFUL TERMINAL

SOURCE RELATIONSHIP IS NOT YET PROJECTABLE WITHOUT GUESSING
-> HELD
```

The Board should make the causal neighborhood needed for understanding source-addressable from the selected human feature coordinate. It does not have to flatten every orthogonal relationship into one graph.

### Proof follows the feature claim

"End-to-end" does not replace rightful proof surfaces with one universal test.

```text
semantic law
    -> focused source/unit proof

relationship / convergence / currentness
    -> focused relationship proof

platform realization / sustained lifetime
    -> Android/native proof where implicated

provider behavior
    -> provider/lived proof where implicated

presentation
    -> render/device proof where implicated

whole human journey
    -> Journey/lived feature proof when that is the claim
```

A green proof at one boundary does not silently prove the others.

## Audit method

### Pass A — Screen and control census

For each of the 13 current screens:

1. enumerate registered/realized elements;
2. distinguish interactive controls from content/containers;
3. resolve every pathway-bearing control;
4. record controls that are intentionally held/unprojected;
5. do not treat every element without a pathway as missing behavior.

### Pass B — Pathway relationship walk

For each of the 71 current pathways:

```text
Surface
  what does the human see/touch?

Structure
  what source/container/identity owns it?

Behavior
  what does the interaction mean?
  who owns the semantic decision?

Depth
  what realizes it?
  what outside truth participates?
  what relationship/currentness/reconciliation is source-proven?
  how does truth return?
  where does the returned truth become human-facing meaning again?
```

Follow exact source, not labels alone.

### Pass C — Depth terminal check

For every path with Depth, classify its terminal:

```text
RIGHTFUL_TERMINAL
    current source really ends at this provider/store/realization boundary

RETURN_COMPLETE
    source return to Family/Projection is perceptible

PARTNER_COMPLETE
    external participant is visible through the source-earned
    Partner / Connection / Conversion / Signal / Observation / Receiver chain

HELD_SOURCE_AMBIGUOUS
    source relationship exists but cannot be projected truthfully yet

PROJECTION_STOPS_EARLY
    current source proves a deeper/rightful relationship that Lens omits
```

Priority witnesses:

```text

    current Direct Family
    -> Method / Execution
    -> Player Partner request
    -> later Player Signal
    -> Store
    -> same Family

CGM / Insulin Partner labs
    Partner
    -> Connection
    -> Conversion
    -> Source / Signal
    -> Observation / Receiver
    -> Store
    -> source-addressed observation / Family consequence

Store-ending direct registrations
    review individually
    never upgrade to Partner by analogy
```

### Pass D — newer stable relationships

Ask whether current Screen Lens makes these relationships perceivable where source earns them:

```text
Service-host sustained realization
Widget / system-surface manifestation
Relay / convergence
construction/lifetime
chronology
presentation return
```

Do not add a `SERVICE`, `WIDGET` or `RELAY` role merely for naming symmetry. Existing role/edge vocabulary may already be enough.

### Pass E — repair only proven gaps

A repair must name:

```text
screen / control / pathway
exact Android source evidence
current Lens projection
missing or misleading relationship
smallest rightful VexBoard owner
regression proof
generated-currentness consequence
```

A repair is not complete merely because the graph is deeper. It should preserve the smallest source-proven causal neighborhood needed to understand the feature, including a return/presentation relationship when source proves one, while remaining generic across features that share the same relationship shape.

Permanent:

```text
VEXBOARD REPAIR != ANDROID SEMANTIC REWRITE
LENS JSON != HAND-AUTHORED SOURCE
PUBLIC DOC WORDING != LENS SOURCE INPUT
CURRENT SOURCE RELATIONSHIP -> PROJECTION
NOT
DESIRED PROJECTION -> INVENTED SOURCE RELATIONSHIP
```

### Two generic projector failures

The audit reduced the repair pressure to two reusable failures:

```text
1. REALIZATION TOPOLOGY LOSS

RealizationWalker already follows nested composable calls and provenance.
The generated realization contract keeps a flat realizer set but discards the
caller -> callee topology. Source-expression Depth therefore often collapses
rich known realization to one render-entry node.

2. DOORWAY-DEPENDENT SOURCE FOLLOWING

invoke(AppActions.X)
    -> shallow direct-registration receiver heuristic

localEffect()
    -> several deeper source-shape followers

custom realization
    -> recursive source walker

Equivalent source richness can therefore become differently visible because of
doorway syntax rather than architectural truth.
```

The first implementation pressure is deliberately smaller than the whole second problem:

> Preserve source-owned realization call relationships that the existing walker already discovers, carry them through the existing realization contract, and expose them through Source-expression Depth. Then inspect the newly visible real Screens before generalizing the next missing relationship.

This changes no Android meaning and earns no new architecture role.
