# VexWork repository router

`[VXG RealForever]`

This file routes work. It intentionally stays small.

## Enter

For substantial VexWork work:

1. read `docs/CULTURE.md`;
2. read `docs/foundation/INDEX.md`;
3. follow the exact implicated foundation;
4. inspect its canonical source and tests;
5. change the smallest rightful owner;
6. prove the claim you actually make.

```text
README.md
-> AGENTS.md
-> docs/CULTURE.md
-> docs/foundation/INDEX.md
   -> exact foundation doc
   -> exact source
   -> exact tests
```

Do not broad-read every connected repository. The Repository Graph tells you where a work item points; the target repository's own current entry/culture source tells you how that repository thinks.

## Contextual integrity routing

Security is durable source, not ambient model context. Do **not** load the Security Assurance corpus or run a security checklist merely because work is being resumed.

At substantial work entry/resume, form one cheap routing question from the exact Work outcome and surface actually being changed:

> **Does this work introduce, change, or materially depend on an identity/trust, authority/effect, sensitive-data/secret, external/provider/network, model/context/memory/tool, build/release/update, or recovery/replay boundary whose failure could permit unauthorized action, disclosure, integrity loss, or material availability loss?**

```text
NO
  -> continue ordinary work
  -> no Security Assurance descent is required

YES
  -> descend only to the relevant Security Lens / Atlas neighborhood
  -> use current evidence and the smallest sufficient verification mode

UNKNOWN
  -> ground only enough source/evidence to decide applicability
  -> UNKNOWN does not justify a broad ambient security audit
```

Repository membership, historical security work, or the mere existence of an old UNKNOWN is not by itself a trigger. The trigger comes from the **current work's meaning or changed boundary**.

When the answer is YES or materially UNKNOWN, route to:

```text
projects/vex-security-assurance/README.md
```

```text
SECURITY_SOURCE != MODEL_CONTEXT
WORK_RESUME != SECURITY_REVIEW
SECURITY_RELEVANCE -> SELECTIVE_SOURCE_DESCENT
```

## Merge-ready rule

For repository candidates, exact candidate proof and current-main integration are separate stages.

```text
prove exact branch/head/tree
-> review / assurance as required
-> READY_FOR_INTEGRATION
-> stop chasing moving main
-> Integration Steward rebinds current main at merge time
```

Unrelated movement of `main` is coordination context, not candidate failure. Do not re-run SourceOwner or rebuild a valid host carrier merely because `main` advanced unless the candidate itself changed or the candidate-owned proof genuinely depends on newly changed main-owned inputs.

When a candidate is ready, descend to:

```text
docs/foundation/REPOSITORY-INTEGRATION.md
docs/process/INTEGRATE-READY-PULL-REQUESTS.md
```

A lane that reaches merge-ready may temporarily become the Integration Steward, but it inherits the existing queue and services higher-priority admissible entries before its own.

## Foundation law

A strange name or boundary should become a question before it becomes a rewrite.

```text
intention before syntax
foundation before feature
map first; depth second
one work truth owner; bounded projections
naming follows the boundary
proof follows the claim
```

VexWork does not consolidate another repository's culture into its own. It points to the rightful culture/source owner and descends when that repository becomes material.
